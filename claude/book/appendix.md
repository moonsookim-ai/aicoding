## 어떤 일에 무엇을 쓸까

이 책에서 다룬 도구는 여럿이지만, 같은 일을 두고 여러 도구가 떠오를 때가 많다. 아래 표는 일의 모습에서 출발해 먼저 꺼낼 도구를 고르게 돕는다. 한 가지 일에 도구 하나만 쓰라는 뜻은 아니다. 스킬은 채팅·Cowork·Claude Code 어디서나 불리고, 연결자는 예약 작업의 재료가 된다. 요금제와 회사 설정에 따라 쓸 수 있는 도구가 다르니, 화면에 보이지 않으면 2단계와 관리자 설정부터 확인한다.

| 일의 모습 | 맞는 도구 | 이유 | 단계 |
|---|---|---|---|
| 짧게 묻고 바로 답을 받는다. 문장 다듬기, 아이디어 몇 개 | Claude 채팅 | 한두 번 주고받으면 끝나고, 걸음마다 내가 고를 수 있다 | 1·9단계 |

| 만든 웹페이지가 사용자 눈에 제대로 보이는지 확인한다 | Claude in Chrome | 처음 쓰는 사용자처럼 입력하고 눌러 보며 문제 목록을 적는다 | 39단계 |
| 같은 설명·양식·말투를 매번 되풀이한다 | 스킬 | 한 번 적어 두면 설명 한 문장에 맞는 요청이 올 때 불려 나온다 | 41~50단계 |
| 자료가 드라이브·메일·메신저·업무 도구 안에 있다 | 연결자 | 복사해 붙이지 않고 Claude가 직접 가서 읽는다. 권한이 분명하다 | 61~69단계 |
| 매주·매월 정해진 때 같은 결과물이 필요하다 | 예약 작업 | 손으로 다듬은 지시를 정해진 때 다시 돌린다 | 73·74단계 |
| 새 메일·새 양식 응답이 들어오면 여러 서비스를 잇는다 | 외부 자동화 도구(Zapier·Make·n8n) | 신호를 받아 Claude를 한 단계로 부르고, 결과를 시트·메신저로 넘긴다 | 75·76단계 |
| 우리 회사 시스템 안에서 화면 없이 Claude를 부른다 | API | 사람이 창을 열지 않아도 시스템이 직접 호출하고, 사용량을 따로 관리할 수 있다 | 96·97단계 |
| 끝에 발송·결제·삭제·제출이 붙은 일 | 어느 도구든 승인 단계를 둔다 | 되돌릴 수 없는 버튼은 사람이 누른다 | 40·68·77단계 |

### 헷갈릴 때 묻는 세 가지 질문

1. **결과가 화면에서 끝나는가, 파일로 남아 누군가에게 넘어가는가?** 화면에서 끝나면 채팅으로 충분하다. 파일로 남고 여러 걸음을 거친다면 Cowork나 Claude Code 쪽이다(51단계).
2. **재료는 어디에 있는가?** 머릿속이나 파일 몇 개라면 채팅, 폴더째라면 Cowork·Claude Code, 회사 도구 안이라면 연결자, 웹 화면에만 있다면 Claude in Chrome이다. 연결자가 있는지 먼저 보고, 없으면 내려받을 수 있는지 보고, 둘 다 안 될 때 브라우저를 쓴다(39단계).
3. **누가 시작 버튼을 누르는가?** 내가 누르면 지금 쓰는 도구 그대로, 정해진 시각이나 새 메일 같은 신호가 누르면 예약 작업이나 외부 자동화 도구, 우리 회사 시스템이 누르면 API다(73단계).

## 가장 자주 빠지는 다섯 가지 함정 (91단계)

| 막히는 곳 | 이렇게 푼다 |
|---|---|
| 흐린 지시 | 누가 읽는지, 어디에 쓰는지를 한 문장씩 덧붙인다 |
| 빠진 맥락 | 자주 쓰는 맥락은 프로젝트 지침에 넣어 둔다 |
| 한꺼번에 맡기기 | 일을 단계로 쪼개고, 단계마다 결과를 확인한다 |
| 확인 생략 | 숫자·인용·고유명사는 반드시 출처와 대조한다 |
| 받은 글 그대로 내보내기 | 내 이름으로 나가는 글은 적어도 한 번은 직접 고쳐 쓴다 |

## 현장에서 자주 본 실패 열 가지

수업과 도입 현장에서 되풀이해 본 실패를 모았다. 대부분 기능을 몰라서 생긴 일이 아니었다. 바쁜 날 확인 한 번을 건너뛰었거나, 처음 정한 원칙을 편의 때문에 조금씩 느슨하게 풀었을 때 생겼다. 각 항목의 단계를 다시 펼쳐 보면 막는 방법이 이미 본문에 있다.

### 1. 기밀 자료를 그대로 올렸다

**증상.** 급한 마음에 고객 명단이 붙은 엑셀이나 아직 발표하지 않은 실적 자료를 통째로 올렸다. 나중에 회사 규정을 보니 외부 서비스에 올리면 안 되는 등급이었다.

**왜 생기나.** 올려도 되는 것과 안 되는 것의 경계를 미리 정해 두지 않았다. 경계가 없으면 그때그때 마감이 기준이 된다. 개인 계정과 회사 계정을 섞어 쓰는 것도 원인이다.

**다시 하지 않으려면.** 8단계에서 올려도 되는 자료와 안 되는 자료를 한 장으로 정해 두고, 실습과 시험에는 가공 자료를 쓴다. 이름·연락처는 지우거나 바꾼 뒤 올린다(3단계). 팀 단위라면 98단계에서 데이터 등급마다 쓸 수 있는 기능을 정한다.

### 2. 확인 없이 발송됐다

**증상.** 초안만 만들라고 했는데 메일이 거래처로 나갔다. 또는 자동화가 만든 답변이 사람 눈을 거치지 않고 고객에게 갔다.

**왜 생기나.** 쓰기 권한과 발송 권한을 나누지 않았고, 흐름의 끝에 승인 단계를 두지 않았다. 몇 번 잘 돌고 나면 확인이 번거롭게 느껴져 빼 버리는 경우도 많다.

**다시 하지 않으려면.** 발송·결제·삭제·제출 앞에는 반드시 사람이 누르는 승인 단계를 둔다(77단계). 연결자는 초안 저장까지만 허용하고 보내기는 사람이 한다(68단계). 브라우저 작업에서도 마지막 버튼은 사람이 누른다(38·40단계).

### 3. 한 대화에 여러 일을 섞었다

**증상.** 보고서 요약, 거래처 메일, 표 정리를 한 대화에서 이어 시켰더니, 앞의 조건이 뒤 일에 섞여 들어가고 어디서 틀렸는지 찾을 수 없게 됐다.

**왜 생기나.** Claude는 한 대화의 앞선 말을 모두 맥락으로 삼는다. 주제가 바뀌어도 앞 내용이 남아 있고, 대화가 길어질수록 앞의 약속을 흘리기 쉽다.

**다시 하지 않으려면.** 새 일은 새 대화에서 시작한다(2단계). 맡기는 일은 한 번에 하나로 나누고 단계마다 결과를 확인한다(60단계). 대화가 무거워지면 요약을 받아 새 대화로 옮긴다(92단계).

### 4. 스킬 설명이 흐려 불리지 않는다

**증상.** 공들여 만든 스킬이 정작 필요한 요청에서 나오지 않는다. 이름을 직접 부르면 잘 되니 스킬 내용에는 문제가 없어 보인다.

**왜 생기나.** 스킬은 맨 위의 설명 한 문장을 보고 불려 나온다. "보고서 관련 스킬"처럼 언제 쓰는지가 빠져 있거나, 실제로 요청할 때 쓰는 말과 설명의 말이 어긋나면 불리지 않는다.

**다시 하지 않으려면.** 설명에 언제 쓰는지와 실제 요청 표현을 넣는다(45단계). 불려야 할 요청과 불리면 안 되는 요청을 몇 개씩 적어 시험하고, 어긋나면 본문보다 설명부터 고친다(49단계).

### 5. 연결자에 권한을 넓게 줬다

**증상.** 메일을 읽어 요약만 시키려고 연결했는데, 허락 화면에서 보내기와 지우기까지 모두 허용해 두었다. 누가 무엇을 허락했는지 아무도 기억하지 못한다.

**왜 생기나.** 허락 화면을 읽지 않고 넘겼다. 처음에 넓게 열어 두면 나중에 필요할 때 편하겠다는 생각도 한몫한다.

**다시 하지 않으려면.** 읽기는 넓게, 쓰기는 좁게, 보내기는 확인한 뒤에(68단계). 연결할 때 회사 계정인지와 허락 범위를 확인하고, 쓰지 않는 연결은 끊는다(63·69단계). 브라우저 확장도 필요한 사이트만 열어 둔다(36단계).

### 6. 자동화가 조용히 멈췄다

**증상.** 매주 월요일 도는 줄 알았던 보고서가 3주째 비어 있었다. 오류 메시지는 어디에도 없었다.

**왜 생기나.** 컴퓨터가 꺼져 있었거나, 연결자 로그인이 만료됐거나, 원본 파일의 이름과 위치가 바뀌었다. 실패를 알려 주는 장치가 없으니 아무도 몰랐다.

**다시 하지 않으려면.** 자동화를 만들 때 실패 알림부터 붙이고, 처음 몇 주는 결과를 직접 확인한다(74·78단계). 담당자가 바뀌면 자동화 목록과 주인을 함께 넘긴다(80단계).

### 7. 공개 주소에 실명이 올라갔다

**증상.** 팀에 돌리려고 게시한 도구 링크를 열어 보니 시험 삼아 넣은 직원 이름과 고객사 이름이 그대로 보였다. 링크를 가진 누구나 열 수 있는 방식이었다.

**왜 생기나.** 공개 범위를 읽지 않고 게시 버튼을 눌렀다. 만들 때 넣은 예시 데이터가 실제 자료였다는 것도 잊었다.

**다시 하지 않으려면.** 게시 전에 공개 범위를 읽고 밖에 나가면 안 되는 내용을 걸러 낸다(21단계). 만들 때부터 가공 자료만 넣고(8단계), 배포한 도구를 시험할 때는 연습용 데이터를 쓴다(39단계). 게시 취소 방법도 미리 알아 둔다.

### 8. API 키가 노출됐다

**증상.** 배포한 페이지 코드에 인증키가 그대로 들어 있었다. 대화창에 키를 붙여 넣어 Claude에게 건넨 적도 있다.

**왜 생기나.** 키를 비밀번호처럼 다루지 않았다. 화면 코드에 적은 값은 브라우저에서 누구나 볼 수 있고, 저장소에 한 번 올라간 키는 지워도 기록에 남는다.

**다시 하지 않으려면.** 키는 환경변수에 넣고, 키가 필요한 요청은 서버 쪽에서 보내게 한다(31단계). 키는 쓰임새가 드러나는 이름으로 따로 만들고, 새어 나간 것 같으면 바로 폐기하고 새로 만든다(75·96단계). 토큰과 키는 대화창에 붙이지 않는다(28단계).

### 9. 평가 없이 지시문을 고쳤다

**증상.** 한 건의 잘못을 고치려고 스킬 지시문에 한 문장을 넣었더니, 예전에 잘 되던 다른 요청이 망가졌다. 몇 주 뒤에야 알았다.

**왜 생기나.** 고친 뒤 예전에 되던 것이 여전히 되는지 확인할 시험이 없었다. 눈앞의 한 건만 보고 판단했다.

**다시 하지 않으려면.** 좋은 결과의 조건을 먼저 적고(93단계), 대표 과제 몇 개로 평가 세트를 만들어 고칠 때마다 같은 시험을 다시 돌린다(94단계). 수정은 기록으로 남기고 사람이 승인한 뒤 반영한다(95단계).

### 10. 도입을 한 사람에게만 맡겼다

**증상.** 열성적인 한 사람이 스킬과 자동화를 잔뜩 만들었는데, 그 사람이 부서를 옮기자 아무도 고칠 줄 몰라 전부 멈췄다.

**왜 생기나.** 요령이 개인의 폴더와 머릿속에만 있었다. 팀 공용으로 올리지 않았고, 누가 무엇을 맡는지도 정하지 않았다.

**다시 하지 않으려면.** 스킬은 조직 단위로 올려 나눠 쓰고(50단계), 잘 되는 프롬프트·스킬·연결자를 팀 표준으로 모아 주인과 점검 주기를 정한다(99단계). 자동화마다 주인을 한 명 정하고(80단계), 로드맵에는 확인 지점과 받는 부서를 적고(90단계), 운영 규칙을 한 장으로 남긴다(100단계).

## 회사에서 쓰기 전 보안·개인정보 점검표

IT·법무 담당과 함께 보는 한 장이다. 본문 곳곳에 흩어진 보안 원칙을 도구별로 모았다. 항목 끝의 숫자는 자세한 설명이
있는 단계다. 회사에 정보보안 규정이 이미 있다면 그 규정이 먼저고, 이 표는 규정을 Claude의 기능마다 붙여 보는
용도로 쓴다. 우리 회사에 해당하지 않는 항목은 지우고, 모르는 항목은 비워 둔 채 누가 언제까지 확인할지 적는다.
어떤 항목이든 메일 발송, 결제, 삭제, 제출, 외부 공개는 사람이 마지막에 확인한다는 원칙이 그 위에 있다.

## 비용 감 잡기

이 책은 요금과 한도의 구체적인 값을 적지 않는다. 자주 바뀌기 때문이다. 대신 비용이 어디서 나가는지, 무엇을 하면
빨리 늘고 무엇을 하면 덜 드는지, 우리 일의 비용을 어떻게 직접 재는지를 모았다. 숫자는 늘 공식 안내에서 확인한다.

### 먼저 알아 둘 세 가지

**앱 구독과 API는 따로 청구된다.** Claude 앱(웹·데스크톱·모바일)을 쓰는 요금제와, 외부 자동화 도구나 회사 시스템이
Claude를 부를 때 쓰는 API는 결제하는 곳도 청구서도 다르다. 앱 구독이 있어도 API 사용료는 Claude Console에서 따로
결제한다(75단계). 외부 자동화 도구를 쓴다면 그 도구의 요금이 또 따로 붙는다(79·97단계).

**요금제마다 쓸 수 있는 기능과 사용량 한도가 다르다.** 프로젝트, Claude Code, Cowork, Claude in Chrome 같은 기능이
어느 요금제부터 열리는지, 일정 시간 동안 얼마나 쓸 수 있는지는 요금제마다 다르고 수시로 바뀐다. 새 부를 시작할
때마다 다시 확인한다(2단계). API에도 따로 한도가 있다(79단계).

**회사 전체로 보면 세 갈래다.** 사람이 쓰는 계정은 사람 수에 따라, API는 쓴 만큼, 외부 자동화 도구는 그 도구의 요금에
API 비용이 더해져 나간다. 가장 자주 빠지는 것은 부서 카드로 따로 결제한 외부 자동화 도구다(97단계).

### 사용량을 빨리 쓰는 일과 덜 쓰는 요령

| 사용량을 빨리 쓰는 일 | 왜 | 덜 쓰는 요령 | 본문 |
|---|---|---|---|
| 한 대화를 주제가 바뀐 뒤에도 계속 이어 쓴다 | 앞의 대화 전체가 매번 맥락으로 함께 간다 | 과제가 바뀌면 새 대화를 연다. Claude Code에서는 `/clear` | 2·26단계 |
| 같은 과제의 대화가 길어진다 | 대화가 맥락 공간을 많이 차지한다. 앞의 약속도 흐려진다 | Claude Code는 `/compact`로 줄이고, `/context`로 얼마나 찼는지 본다. 앱에서는 인수인계 요약을 받아 새 대화로 옮긴다 | 26·92단계 |
| 큰 파일이나 긴 첨부를 통째로 보낸다 | 보내는 글의 양만큼 쓴다 | 필요한 부분만 잘라 보내거나 요약된 표만 보낸다 | 14·79단계 |
| 쉬운 분류·요약까지 무거운 모델과 확장 사고로 돌린다 | 무거운 모델일수록 1회 비용이 크다 | 쉬운 일은 빠른 모델로, 어려운 판단에만 깊은 모델을 쓴다. 가벼운 모델로 먼저 거르고 필요한 건만 깊게 읽힌다 | 2·79·97단계 |
| 에이전트에게 긴 작업을 통째로 맡긴다 | 헤매며 단계가 늘면 사용량도 는다 | 일을 단계로 쪼개고, 판단이 들어간 단계 뒤에서 멈춰 확인한다. 평가 세트로 단계 수가 늘었는지 본다 | 92·94단계 |
| 자동화가 건마다, 매시간 돈다 | 사람이 자는 동안에도 실행 횟수만큼 쓴다 | 하루 한 번 모아서 돌리고, 트리거 조건을 좁힌다 | 73·79·97단계 |
| 흐름 속 지시문과 예시를 길게 늘린다 | 자료가 짧아도 지시문과 예시가 매번 함께 간다 | 지시문은 필요한 규칙만 남기고, 예시는 한두 개로 줄인다 | 79단계 |
| 실패한 실행이 다시 돌고, 시험 실행이 쌓인다 | 재시도와 시험도 사용량에 잡힌다 | 같은 입력이 다시 들어오면 새로 돌지 않게 조건을 둔다. 시험 실행은 계산표에 따로 적는다 | 79단계 |
| 같은 배경 설명을 대화마다 새로 쓰고, 빠뜨려 다시 받는다 | 다시 묻고 다시 받는 대화가 늘어난다 | 자주 쓰는 설명은 프로젝트 지침·스킬·CLAUDE.md에 한 번 적어 둔다. 다만 너무 길게 쓰지 않는다 | 5·26·41단계 |

### 직접 재는 법

요금표만 보고 짐작하지 않는다. Claude에게 요금을 물어서 계산하지도 않는다. 기억에 기댄 답은 이미 바뀐 값일 수 있다.

1. **샘플로 돌린다.** 평범한 건과 긴 건을 섞어 몇 번 돌린다. 실제 고객 자료 대신 가공한 샘플을 쓴다(79단계).
2. **사용량 화면을 본다.** API는 Claude Console의 사용량 화면에서, 팀 요금제는 관리자 화면에서, Claude Code는 `/usage`
   (`/cost`는 같은 명령의 다른 이름)로 실제로 쓴 양을 확인한다. 메뉴 이름과 위치는 바뀔 수 있으니 화면에서 찾는다.
3. **1회 비용을 정한다.** 확인한 사용량과 공식 요금표로 1회 비용을 구한다. 평범한 건과 긴 건의 값이 크게 다르면 그
   사이 어디쯤으로 잡는다.
4. **곱한다.** 한 달 실행 횟수 × 1회 비용. 실행 횟수는 성공한 횟수가 아닌 실제로 돈 횟수다. 가장 몰리는 날의 횟수도
   따로 적는다. 한도에는 한 달 합계보다 그 며칠이 먼저 닿는다.
5. **첫 달 말에 맞춰 본다.** 실제 사용량을 계산표와 비교하고, 크게 다르면 긴 입력·재시도·시험 실행부터 찾는다.

### 계산표 (자동화 하나, 79단계 방식)

요금 숫자는 공식 요금표를 보고 사람이 채운다. 요금표를 본 날짜를 함께 적어 두면 석 달 뒤 다시 계산할 때 무엇이
바뀌었는지 가늠하기 쉽다.

흐름 이름: ____________   트리거: ____________   작성한 사람: ________   작성일: ________

| 항목 | 숫자 | 어디서 가져왔나 | 확인한 날짜 |
|---|---|---|---|
| 한 달 실행 횟수 | | 시각 트리거는 달력, 사건 트리거는 지난 한 달 기록 | |
| 몰리는 날 실행 횟수(그날 날짜) | | 지난 기록에서 가장 많았던 날 | |
| 시험·재시도 실행 횟수 | | 실행 기록 | |
| 1회 Claude 사용량(평범한 건) | | 콘솔·사용량 화면 | |
| 1회 Claude 사용량(긴 건) | | 콘솔·사용량 화면 | |
| 1회 Claude 비용 | | 사용량과 Anthropic 공식 요금표 | |
| 1회 외부 도구 비용 | | 외부 도구의 요금 안내 | |
| 한 달 예상 비용 | | 한 달 실행 횟수 × 1회 비용 | |
| 같은 일을 손으로 할 때의 한 달 비용(선택) | | 한두 주 실제로 잰 시간 × 회사의 시간당 인건비 기준 | |
| 자동화 쪽에 더할 사람 시간(선택) | | 승인·월 점검·고치는 시간 | |
| 판단 | 켠다 / 줄여서 다시 계산한다 / 켜지 않는다 | 이유: | |

|---|---|---|---|---|---|---|---|---|---|---|
| | | | | | | | | | | |

### 월 한도를 걸어 둔다

- API는 키를 만들기 전에 Claude Console에서 월 사용 한도를 먼저 낮게 잡아 둔다. 흐름이 잘못 돌아 같은 요청을 끝없이
  보내도 한도에서 멈춘다(75단계).
- 자동화용 키를 따로 두면 누가 얼마를 썼는지 나눠 보기 쉽고, 자동화가 한도를 다 써서 사람의 작업까지 막히는 일도
  줄어든다(79단계).
- 사용 알림을 설정할 수 있다면 켜 두고, 알림을 받는 사람을 둘 이상으로 한다(78단계).
- 한도와 설정 방법은 요금제마다 다르고 자주 바뀐다. 공식 안내에서 확인한다.

### 언제 다시 계산하나

트리거 조건을 넓혔을 때, 모델을 바꿨을 때, 지시문이나 보내는 자료를 늘렸을 때, 요금이 바뀌었다는 공지를 봤을 때
다시 잰다. 부서마다 일이 몰리는 때(결산 달, 공고 마감 주, 분기 말, 신제품 출시 직후)를 앞두고도 한 번 더 본다(79단계).
