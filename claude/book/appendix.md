### 다섯 칸 질문 틀 (8단계)

**누구로서 · 왜 · 무엇을 · 어디까지 · 어떤 형식으로**. 이 다섯 가지만 채워 넣어도 첫 답부터 달라집니다.

### SKILL.md 네 마디 (48단계)

맨 위에 언제 쓰는 스킬인지 밝히는 설명 한 문장을 두고, 그 아래에 **맡은 자리 · 일하는 순서 · 본보기 ·
결과의 꼴**을 차례로 적습니다.

### 자동화 설계 여섯 줄 (73단계)

무엇을 얻으려는가 → 재료는 어디 있는가 → 어떤 지시를 주는가 → 무엇이 나오는가 → 누가 보는가 → 누구에게 가는가

## 어떤 일에 무엇을 쓸까

이 책에서 다룬 도구는 여럿이지만, 같은 일을 두고 여러 도구가 떠오를 때가 많습니다. 아래 표는 일의 모습에서 출발해 먼저 꺼낼 도구를 고르게 돕습니다. 한 가지 일에 도구 하나만 쓰라는 뜻은 아닙니다. 스킬은 채팅·Cowork·Claude Code 어디서나 불리고, 연결자는 예약 작업의 재료가 됩니다. ChatGPT와 Codex도 스킬을 함께 씁니다. ChatGPT나 Codex에서 같은 일을 할 때 쓰는 기능 이름은 「ChatGPT·Codex에서」 열에 적었습니다. 요금제와 회사 설정에 따라 쓸 수 있는 도구가 다르니, 화면에 보이지 않으면 2단계와 관리자 설정부터 확인합니다.

### 헷갈릴 때 묻는 세 가지 질문

1. **결과가 화면에서 끝납니까, 파일로 남아 누군가에게 넘어갑니까?** 화면에서 끝나면 채팅(ChatGPT의 Chat)으로 충분합니다. 파일로 남고 여러 걸음을 거친다면 Cowork나 Claude Code, ChatGPT라면 Work나 Codex 쪽입니다(31·56단계).
2. **재료는 어디에 있습니까?** 머릿속이나 파일 몇 개라면 채팅, 폴더째라면 Cowork·Claude Code, 회사 도구 안이라면 연결자, 웹 화면에만 있다면 Claude in Chrome이나 ChatGPT의 브라우저 기능, 데스크톱 앱 안에만 있다면 컴퓨터 사용입니다. 연결자가 있는지 먼저 보고, 없으면 내려받을 수 있는지 보고, 둘 다 안 될 때 브라우저를, 브라우저로도 안 될 때 컴퓨터 사용을 씁니다(44·45단계).
3. **누가 시작 버튼을 누릅니까?** 내가 누르면 지금 쓰는 도구 그대로, 정해진 시각이나 새 메일 같은 신호가 누르면 예약 작업이나 외부 자동화 도구, 우리 회사 시스템이 누르면 API나 `codex exec`입니다(37·74단계).

## 현장에서 자주 본 실패 열 가지

수업과 도입 현장에서 되풀이해 본 실패를 모았습니다. 대부분 기능을 몰라서 생긴 일이 아니었습니다. 바쁜 날 확인 한 번을 건너뛰었거나, 처음 정한 원칙을 편의 때문에 조금씩 느슨하게 풀었을 때 생겼습니다. 각 항목의 단계를 다시 펼쳐 보면 막는 방법이 이미 본문에 있습니다.

### 1. 기밀 자료를 그대로 올렸다

**증상.** 급한 마음에 고객 명단이 붙은 엑셀이나 아직 발표하지 않은 실적 자료를 통째로 올렸습니다. 나중에 회사 규정을 보니 외부 서비스에 올리면 안 되는 등급이었습니다.

**왜 생기나.** 올려도 되는 것과 안 되는 것의 경계를 미리 정해 두지 않았습니다. 경계가 없으면 그때그때 마감이 기준이 됩니다. 개인 계정과 회사 계정을 섞어 쓰는 것도 원인입니다.

**다시 하지 않으려면.** 7단계에서 올려도 되는 자료와 안 되는 자료를 한 장으로 정해 두고, 실습과 시험에는 가공 자료를 씁니다. 이름·연락처는 지우거나 바꾼 뒤 올립니다(3단계). 팀 단위라면 98단계에서 데이터 등급마다 쓸 수 있는 기능을 정합니다.

### 2. 확인 없이 발송됐다

**증상.** 초안만 만들라고 했는데 메일이 거래처로 나갔습니다. 또는 자동화가 만든 답변이 사람 눈을 거치지 않고 고객에게 갔습니다.

**왜 생기나.** 쓰기 권한과 발송 권한을 나누지 않았고, 흐름의 끝에 승인 단계를 두지 않았습니다. 몇 번 잘 돌고 나면 확인이 번거롭게 느껴져 빼 버리는 경우도 많습니다.

**다시 하지 않으려면.** 발송·결제·삭제·제출 앞에는 반드시 사람이 누르는 승인 단계를 둡니다(77단계). 연결자는 초안 저장까지만 허용하고 보내기는 사람이 합니다(70단계). 브라우저 작업에서도 마지막 버튼은 사람이 누릅니다(43·46단계).

### 3. 한 대화에 여러 일을 섞었다

**증상.** 보고서 요약, 거래처 메일, 표 정리를 한 대화에서 이어 시켰더니, 앞의 조건이 뒤 일에 섞여 들어가고 어디서 틀렸는지 찾을 수 없게 됐습니다.

**왜 생기나.** Claude는 한 대화의 앞선 말을 모두 맥락으로 삼습니다. 주제가 바뀌어도 앞 내용이 남아 있고, 대화가 길어질수록 앞의 약속을 흘리기 쉽습니다.

**다시 하지 않으려면.** 새 일은 새 대화에서 시작합니다(2단계). 맡기는 일은 한 번에 하나로 나누고 단계마다 결과를 확인합니다(63단계). 대화가 무거워지면 요약을 받아 새 대화로 옮깁니다(92단계).

### 4. 스킬 설명이 흐려 불리지 않는다

**증상.** 공들여 만든 스킬이 정작 필요한 요청에서 나오지 않습니다. 이름을 직접 부르면 잘 되니 스킬 내용에는 문제가 없어 보입니다.

**왜 생기나.** 스킬은 맨 위의 설명 한 문장을 보고 불려 나옵니다. "보고서 관련 스킬"처럼 언제 쓰는지가 빠져 있거나, 실제로 요청할 때 쓰는 말과 설명의 말이 어긋나면 불리지 않습니다.

**다시 하지 않으려면.** 설명에 언제 쓰는지와 실제 요청 표현을 넣습니다(50단계). 불려야 할 요청과 불리면 안 되는 요청을 몇 개씩 적어 시험하고, 어긋나면 본문보다 설명부터 고칩니다(54단계).

### 5. 연결자에 권한을 넓게 줬다

**증상.** 메일을 읽어 요약만 시키려고 연결했는데, 허락 화면에서 보내기와 지우기까지 모두 허용해 두었습니다. 누가 무엇을 허락했는지 아무도 기억하지 못합니다.

**왜 생기나.** 허락 화면을 읽지 않고 넘겼습니다. 처음에 넓게 열어 두면 나중에 필요할 때 편하겠다는 생각도 한몫합니다.

**다시 하지 않으려면.** 읽기는 넓게, 쓰기는 좁게, 보내기는 확인한 뒤에(70단계). 연결할 때 회사 계정인지와 허락 범위를 확인하고, 쓰지 않는 연결은 끊습니다(65·71단계). 브라우저 확장도 필요한 사이트만 열어 둡니다(41단계).

### 6. 자동화가 조용히 멈췄다

**증상.** 매주 월요일 도는 줄 알았던 보고서가 3주째 비어 있었습니다. 오류 메시지는 어디에도 없었습니다.

**왜 생기나.** 컴퓨터가 꺼져 있었거나, 연결자 로그인이 만료됐거나, 원본 파일의 이름과 위치가 바뀌었습니다. 실패를 알려 주는 장치가 없으니 아무도 몰랐습니다.

**다시 하지 않으려면.** 자동화를 만들 때 실패 알림부터 붙이고, 처음 몇 주는 결과를 직접 확인합니다(74·78단계). 담당자가 바뀌면 자동화 목록과 주인을 함께 넘깁니다(80단계).

### 7. 공개 주소에 실명이 올라갔다

**증상.** 팀에 돌리려고 게시한 도구 링크를 열어 보니 시험 삼아 넣은 직원 이름과 고객사 이름이 그대로 보였습니다. 링크를 가진 누구나 열 수 있는 방식이었습니다.

**왜 생기나.** 공개 범위를 읽지 않고 게시 버튼을 눌렀습니다. 만들 때 넣은 예시 데이터가 실제 자료였다는 것도 잊었습니다.

**다시 하지 않으려면.** 게시 전에 공개 범위를 읽고 밖에 나가면 안 되는 내용을 걸러 냅니다(19단계). 만들 때부터 가공 자료만 넣고(7단계), 배포한 도구를 시험할 때는 연습용 데이터를 씁니다(45단계). 게시 취소 방법도 미리 알아 둡니다.

### 8. API 키가 노출됐다

**증상.** 배포한 페이지 코드에 인증키가 그대로 들어 있었습니다. 대화창에 키를 붙여 넣어 Claude에게 건넨 적도 있습니다.

**왜 생기나.** 키를 비밀번호처럼 다루지 않았습니다. 화면 코드에 적은 값은 브라우저에서 누구나 볼 수 있고, 저장소에 한 번 올라간 키는 지워도 기록에 남습니다.

**다시 하지 않으려면.** 키는 환경변수에 넣고, 키가 필요한 요청은 서버 쪽에서 보내게 합니다(28단계). 키는 쓰임새가 드러나는 이름으로 따로 만들고, 새어 나간 것 같으면 바로 폐기하고 새로 만듭니다(75·96단계). 토큰과 키는 대화창에 붙이지 않습니다(25단계).

### 9. 평가 없이 지시문을 고쳤다

**증상.** 한 건의 잘못을 고치려고 스킬 지시문에 한 문장을 넣었더니, 예전에 잘 되던 다른 요청이 망가졌습니다. 몇 주 뒤에야 알았습니다.

**왜 생기나.** 고친 뒤 예전에 되던 것이 여전히 되는지 확인할 시험이 없었습니다. 눈앞의 한 건만 보고 판단했습니다.

**다시 하지 않으려면.** 좋은 결과의 조건을 먼저 적고(93단계), 대표 과제 몇 개로 평가 세트를 만들어 고칠 때마다 같은 시험을 다시 돌립니다(94단계). 수정은 기록으로 남기고 사람이 승인한 뒤 반영합니다(95단계).

### 10. 도입을 한 사람에게만 맡겼다

**증상.** 열성적인 한 사람이 스킬과 자동화를 잔뜩 만들었는데, 그 사람이 부서를 옮기자 아무도 고칠 줄 몰라 전부 멈췄습니다.

**왜 생기나.** 요령이 개인의 폴더와 머릿속에만 있었습니다. 팀 공용으로 올리지 않았고, 누가 무엇을 맡는지도 정하지 않았습니다.

**다시 하지 않으려면.** 스킬은 조직 단위로 올려 나눠 쓰고(55단계), 잘 되는 프롬프트·스킬·연결자를 팀 표준으로 모아 주인과 점검 주기를 정합니다(99단계). 자동화마다 주인을 한 명 정하고(80단계), 로드맵에는 확인 지점과 받는 부서를 적고(90단계), 운영 규칙을 한 장으로 남깁니다(100단계).

## 회사에서 쓰기 전 보안·개인정보 점검표

IT·법무 담당과 함께 보는 한 장입니다. 본문 곳곳에 흩어진 보안 원칙을 도구별로 모았습니다. 항목 끝의 숫자는 자세한 설명이

## 비용 감 잡기

이 책은 요금과 한도의 구체적인 값을 적지 않습니다. 자주 바뀌기 때문입니다. 대신 비용이 어디서 나가는지, 무엇을 하면
빨리 늘고 무엇을 하면 덜 드는지, 우리 일의 비용을 어떻게 직접 재는지를 모았습니다. 숫자는 늘 공식 안내에서 확인합니다.

### 먼저 알아 둘 세 가지

**앱 구독과 API는 따로 청구됩니다.** Claude 앱(웹·데스크톱·모바일)을 쓰는 요금제와, 외부 자동화 도구나 회사 시스템이
Claude를 부를 때 쓰는 API는 결제하는 곳도 청구서도 다릅니다. 앱 구독이 있어도 API 사용료는 Claude Console에서 따로
결제합니다(75단계). 외부 자동화 도구를 쓴다면 그 도구의 요금이 또 따로 붙습니다(79·97단계).

**요금제마다 쓸 수 있는 기능과 사용량 한도가 다릅니다.** 프로젝트, Claude Code, Cowork, Claude in Chrome 같은 기능이
어느 요금제부터 열리는지, 일정 시간 동안 얼마나 쓸 수 있는지는 요금제마다 다르고 수시로 바뀝니다. 새 부를 시작할
때마다 다시 확인합니다(2단계). API에도 따로 한도가 있습니다(79단계).

**회사 전체로 보면 세 갈래입니다.** 사람이 쓰는 계정은 사람 수에 따라, API는 쓴 만큼, 외부 자동화 도구는 그 도구의 요금에
API 비용이 더해져 나갑니다. 가장 자주 빠지는 것은 부서 카드로 따로 결제한 외부 자동화 도구입니다(97단계).

**ChatGPT와 Codex도 같은 세 갈래로 봅니다.** ChatGPT 요금제(Free, Go, Plus, Pro, Business, Enterprise, Edu)는 앱 구독이고,
OpenAI API는 따로 결제합니다. Codex는 ChatGPT 계정으로 로그인하면 요금제 한도 안에서 쓰고, API 키로 로그인하면 쓴 만큼
API 요금이 나갑니다. API 키로는 Codex 클라우드 작업과 GitHub 코드 리뷰 같은 클라우드 기능을 쓰지 못합니다. ChatGPT의 Work와
Codex는 요금과 사용량 한도를 함께 씁니다. 한도는 5시간 단위로 걸리고 주간 한도가 따로 걸릴 수 있으며, 내 컴퓨터에서 도는
작업과 클라우드 작업이 같은 한도를 나눠 씁니다. 쓰는 양은 모델, 맥락 크기, 추론 강도에 따라 달라집니다. Plus·Pro는
크레딧을 더 사서 사용량을 늘릴 수 있습니다(31·79단계).

### 직접 재는 법

요금표만 보고 짐작하지 않습니다. Claude에게 요금을 물어서 계산하지도 않습니다. 기억에 기댄 답은 이미 바뀐 값일 수 있습니다.

1. **샘플로 돌립니다.** 평범한 건과 긴 건을 섞어 몇 번 돌립니다. 실제 고객 자료 대신 가공한 샘플을 씁니다(79단계).
2. **사용량 화면을 봅니다.** API는 Claude Console의 사용량 화면에서, 팀 요금제는 관리자 화면에서, Claude Code는 `/usage`
   (`/cost`는 같은 명령의 다른 이름)로 실제로 쓴 양을 확인합니다. Codex는 `/status`·`/usage`나 Codex 사용량 대시보드에서 봅니다. 메뉴 이름과 위치는 바뀔 수 있으니 화면에서 찾습니다.
3. **1회 비용을 정합니다.** 확인한 사용량과 공식 요금표로 1회 비용을 구합니다. 평범한 건과 긴 건의 값이 크게 다르면 그
   사이 어디쯤으로 잡습니다.
4. **곱합니다.** 한 달 실행 횟수 × 1회 비용. 실행 횟수는 성공한 횟수가 아닌 실제로 돈 횟수입니다. 가장 몰리는 날의 횟수도
   따로 적습니다. 한도에는 한 달 합계보다 그 며칠이 먼저 닿습니다.
5. **첫 달 말에 맞춰 봅니다.** 실제 사용량을 계산표와 비교하고, 크게 다르면 긴 입력·재시도·시험 실행부터 찾습니다.

### 월 한도를 걸어 둔다

- API는 키를 만들기 전에 Claude Console에서 월 사용 한도를 먼저 낮게 잡아 둡니다. 흐름이 잘못 돌아 같은 요청을 끝없이

  줄어듭니다(79단계).
- 사용 알림을 설정할 수 있다면 켜 두고, 알림을 받는 사람을 둘 이상으로 합니다(78단계).
- OpenAI API는 누적 결제액에 따라 사용량 등급이 올라가며 월 한도도 함께 바뀝니다. 지출 알림과 월 상한을 거는 화면은 이 판에서 직접 확인하지 못했으니, 조직 설정에서 찾아 확인합니다(79단계).
- 한도와 설정 방법은 요금제마다 다르고 자주 바뀝니다. 공식 안내에서 확인합니다.

### 언제 다시 계산하나

트리거 조건을 넓혔을 때, 모델을 바꿨을 때, 지시문이나 보내는 자료를 늘렸을 때, 요금이 바뀌었다는 공지를 봤을 때
다시 잽니다. 부서마다 일이 몰리는 때(결산 달, 공고 마감 주, 분기 말, 신제품 출시 직후)를 앞두고도 한 번 더 봅니다(79단계).

## 인기 스킬과 스킬 모음

스킬을 처음부터 만들기 전에 이미 공개된 스킬을 먼저 살펴봅시다. 잘 만든 스킬의 SKILL.md를 읽어 보는 것만으로도 48단계의 네 마디가 어떻게 쓰이는지 보입니다. 남이 만든 스킬은 설치하기 전에 폴더 안의 파일을 열어 무엇을 하는지 확인합니다. 특히 스크립트가 들어 있으면 IT 담당과 함께 봅니다.
