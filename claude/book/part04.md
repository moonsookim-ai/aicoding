# 제4부 · Codex로 직접 만들기

월요일 아침 주간 회의에서 누리상사 경영지원팀 오세린 차장은 제3부의 방법으로 만든 비품 신청 페이지를 화면에 띄웠습니다. 한 달 동안 신청이 백 건 넘게 들어왔고, 메일로 받은 신청을 엑셀에 옮겨 적던 일은 사라졌습니다. 발표가 끝나자 팀장이 한 가지를 물었습니다. "이거 Claude가 만들고 Claude가 확인한 거죠? 다른 눈으로 본 적은 있어요?" 오 차장은 바로 답하지 못했습니다.

30단계에서 우리는 "다 됐다"는 말을 그대로 믿지 않는 법을 익혔습니다. 바뀐 파일을 묻고, 배포된 주소를 직접 열고, 테스트를 되돌려 시험했습니다. 그래도 남는 빈틈이 있습니다. 만든 쪽과 검토한 쪽이 같은 에이전트라면 같은 가정 안에서 보게 됩니다. 29단계의 서브에이전트가 그 빈틈을 조금 줄였다면, 이번 부에서는 아예 다른 회사가 만든 에이전트를 옆에 둡니다. OpenAI의 Codex입니다. 훈련 방식과 습관이 다른 에이전트는 놓치는 곳도 다를 가능성이 큽니다. 회사가 이미 ChatGPT 요금제를 쓰고 있다면 새로 도입할 것도 많지 않고, 한쪽 도구가 멈추거나 사용량 한도에 걸린 날에도 일을 이어 갈 수 있습니다.

Codex는 터미널에서 쓰는 CLI, ChatGPT 데스크톱 앱 안의 Codex, 웹(chatgpt.com/codex)의 클라우드 작업, GitHub의 코드 리뷰까지 여러 곳에서 씁니다. 겉모습은 달라도 제3부에서 익힌 원리는 그대로 통합니다. 규칙은 파일에 적고, 큰일은 계획부터 받고, 작업 전후로 커밋하고, 끝났다는 보고는 직접 확인합니다. 이름이 바뀌는 곳이 몇 군데 있을 뿐입니다. CLAUDE.md는 AGENTS.md가 되고, 허락 요청은 승인 방식과 샌드박스라는 두 층으로 나뉩니다.

이 부는 다음 순서로 진행합니다. 31~34단계에서 Codex를 설치하고 규칙과 권한을 정한 뒤, 코딩 없는 파일 정리로 손을 풉니다. 35~38단계에서는 Codex만의 쓰임새로 넓혀 갑니다. 여러 작업을 클라우드에서 나란히 돌리고, GitHub의 PR 리뷰를 맡기고, 설정과 스킬과 MCP로 범위를 넓히고, 마지막으로 Claude Code와 Codex를 한 저장소에서 함께 씁니다. 39단계에서는 제3부와 제4부에서 만든 도구를 배포된 주소로 발표하며 제2편을 마무리합니다.

| 단계 | 다루는 것 | 손에 남는 것 |
|---|---|---|
| 31단계 | ChatGPT의 Chat·Work·Codex 가운데 어디에 맡길지 | 내 일 세 가지를 어디에 맡길지 적은 목록 |
| 32단계 | Codex 설치, 로그인, 첫 실행 | 버전 번호가 나오는 Codex와 첫 작업 기록 |
| 33단계 | AGENTS.md, 승인 방식과 샌드박스 | 내 저장소의 AGENTS.md와 고른 권한 설정 |
| 34단계 | 코딩 없이 업무 파일 정리에 쓰기 | 검산까지 마친 파일 정리 결과 하나 |
| 35단계 | Local·Worktree·Cloud, 여러 작업 나란히 돌리기 | 클라우드 환경 하나와 PR로 받은 결과 |
| 36단계 | GitHub PR 리뷰를 Codex에게 맡기기 | 리뷰를 켠 저장소, 지적마다 판단을 남긴 PR |
| 37단계 | config.toml, `/` 명령, 스킬, MCP, `codex exec` | 내 설정 파일과 읽기 전용 자동 점검 하나 |
| 38단계 | Claude Code와 Codex 나눠 쓰기, 교차 검토 | 일 나누기 표와 함께 관리하는 규칙 파일 두 개 |
| 39단계 | 제2편 결과물 발표 | 배포된 주소와 교차 검토 기록을 들고 하는 발표 |

미리 밝혀 둡니다. Codex의 명령, 화면 구성, 요금제 범위, 모델 이름은 몇 주 사이에도 바뀝니다. 이 책에 적은 모델 이름과 가격은 집필 시점(2026년 9월) 기준이고, 명령과 메뉴 이름은 길잡이로만 받아들여 주십시오. 실제 절차는 공식 문서(learn.chatgpt.com/docs)에서 확인하시기 바랍니다.

## 31단계 · GPT에게 일을 맡기는 곳: Chat, Work, Codex

> ChatGPT에는 대화하는 Chat, 결과물을 맡기는 Work, 개발을 맡기는 Codex가 있습니다. 무엇을 맡길지 먼저 정하면 어느 문으로 들어갈지는 저절로 정해집니다.

**걸리는 시간** · 읽기 약 15분 · 따라 하기 약 30분

### 이 단계를 마치면
- ChatGPT의 Chat, Work, Codex가 각각 어떤 일에 맞는지 구분해 말할 수 있습니다.
- Codex를 쓰는 다섯 가지 통로와 내 요금제에서 열리는 통로를 확인할 수 있습니다.
- Claude의 채팅, Cowork, Claude Code와 ChatGPT의 세 방식을 짝지어 설명할 수 있습니다.

제3부에서 여러분은 Claude Code로 작업 폴더를 만들고, 규칙 파일을 쓰고, 저장소에 올리고, 주소 하나로 동료에게 도구를 건넸습니다. 그런데 회사에 돌아가면 사정이 다를 수 있습니다. 전사 표준 도구가 ChatGPT로 정해져 있거나, 협력사가 Codex로 만든 저장소를 넘겨주거나, 한 팀 안에서도 쓰는 도구가 갈리기도 합니다. 제4부는 제3부에서 익힌 습관을 그대로 들고 OpenAI의 Codex로 건너가는 과정입니다. 명령과 화면은 조금 달라도 일하는 순서는 같습니다. 폴더를 정하고, 규칙을 적고, 계획을 먼저 받고, 되돌릴 기록을 남기고, 결과를 직접 확인합니다.

먼저 지도를 펼쳐 보겠습니다. ChatGPT는 2026년에 들어 구조가 크게 바뀌었습니다. 예전에 쓰던 캔버스, 커스텀 GPT, ChatGPT agent 같은 이름은 없어졌거나 다른 기능으로 옮겨 가는 중입니다. 몇 해 전 기억으로 메뉴를 찾으면 헤매기 쉽습니다. 이 단계에서는 지금의 이름으로 세 방식을 정리합니다. 아래 내용은 모두 집필 시점(2026년 9월) 기준이며, 이름과 요금은 언제든 바뀔 수 있습니다.

### ChatGPT의 세 가지 방식

지금 ChatGPT에서 일을 맡기는 방식은 세 가지입니다.

| 방식 | 맡기는 일 | 돌아오는 것 | Claude에서 가까운 것 |
|---|---|---|---|
| Chat | 질문, 대화, 짧은 글 다듬기 | 대화 속 답 | Claude 채팅 |
| Work | 문서, 발표 자료, 스프레드시트, PDF, 분석처럼 검토할 결과물 | 미리 보고 내려받는 파일 | Cowork |
| Codex | 코드, 저장소, 명령 실행, 개발 도구가 필요한 일 | 바뀐 파일과 변경 내역(diff), PR | Claude Code |

**Chat**은 제1부에서 익힌 대화 방식입니다. 묻고, 답을 읽고, 다시 묻습니다. **Work**는 결과물까지 맡기는 방식입니다. 원본 파일을 첨부하고 "8장짜리 발표 자료로 만들어 줘"라고 하면, 대화 옆에서 문서를 미리 보고 부분을 지정해 고쳐 달라고 한 뒤 내려받습니다. 웹에서는 입력창 위의 전환기에서 Chat과 Work를 고릅니다. 웹의 Work는 클라우드에서 돌고, 데스크톱 앱에서는 내 컴퓨터에서 도는 "Work locally"와 "Cloud" 가운데 하나를 고를 수 있습니다. **Codex**는 개발을 맡는 방식입니다. 폴더 안 파일을 읽고 고치고, 명령을 실행하고, 결과를 변경 내역으로 보여 줍니다.

모델도 방식에 따라 다릅니다. Work와 Codex에서는 GPT-6 Astra, GPT-6 Sol, GPT-6 Luna 가운데 하나를 고르고 추론 강도를 함께 정합니다. GPT-6 Sol과 Luna는 Chat에서는 쓸 수 없습니다. Chat 쪽 모델 이름은 요즘 몇 주 단위로 바뀌고 있어 이 책에서는 적지 않습니다. 화면의 모델 메뉴에서 확인하세요.

하나 더 알아 둘 점이 있습니다. Work와 Codex는 기능이 겹치고 요금, 크레딧, 사용량 한도를 함께 씁니다. 공식 안내는 이렇게 권합니다. 개발이 아닌 업무는 Work로, 개발 도구와 기술적인 세부가 필요하면 Codex로. 그렇다면 이 책은 왜 개발자가 아닌 독자에게 Codex를 권할까요? 제3부에서 배운 방식이 Codex에서 그대로 통하기 때문입니다. 폴더 하나를 작업 범위로 정하고, 규칙 파일을 두고, 무엇을 허락할지 정하고, Git 기록으로 되돌리는 흐름입니다. 사내 도구를 만들고 고치는 일은 Codex가 맞고, 보고서 한 편을 만드는 일은 대개 Work가 편합니다. 둘 사이에 걸친 일, 예를 들어 폴더 속 파일 수십 개를 규칙대로 정리하는 일은 34단계에서 다시 나눠 봅니다.

### Codex가 쓰이는 곳

Codex는 한 가지 프로그램의 이름으로 끝나지 않습니다. 같은 Codex를 여러 통로로 씁니다.

| 쓰는 곳 | 여는 방법 | 이럴 때 맞습니다 |
|---|---|---|
| 데스크톱 앱 | ChatGPT 데스크톱 앱에서 Codex를 고릅니다 | 터미널이 부담스러울 때. 실행 위치를 Local(지금 폴더), Worktree(Git 워크트리로 격리), Cloud(클라우드 환경) 가운데 고릅니다 |
| CLI | 터미널에서 `codex`를 칩니다 | 제3부처럼 작업 폴더에서 바로 일할 때 |
| IDE 확장 | VS Code, Cursor, Windsurf에 확장을 설치합니다 | 개발자 동료와 같은 편집기에서 일할 때 |
| Codex cloud | 브라우저에서 chatgpt.com/codex를 엽니다 | GitHub 저장소를 연결해 여러 작업을 동시에 돌리고, 결과를 검토해 PR로 만들 때 |
| GitHub | PR 댓글에 `@codex review`를 씁니다 | 올라온 변경을 검토받을 때. Codex cloud 설정이 먼저 돼 있어야 합니다 |

예전에는 "Codex 앱"이 따로 있었지만, 지금은 ChatGPT 데스크톱 앱 안에 Codex가 들어 있습니다. 앱을 열고 ChatGPT와 Codex 가운데 하나를 고르는 식입니다. macOS, Windows, Linux를 모두 지원합니다. 터미널에서 일하다가 화면으로 보고 싶어지면 CLI에서 `codex app`을 실행하거나 `/app`을 입력해 같은 대화를 데스크톱 앱에서 이어 갈 수 있습니다. 이 밖에 ChatGPT 모바일 앱에서 PC의 Codex 작업을 승인하고 결과를 보는 Codex Remote도 있지만, 계정마다 차례로 열리는 기능이라 아직 안 보일 수 있습니다.

이 부에서는 데스크톱 앱과 CLI를 중심으로 설명합니다. 32단계에서 둘 다 설치하고, 33단계에서 규칙과 권한을 정하고, 34단계에서 코드 없는 일부터 맡겨 봅니다.

### 요금제별로 되는 것

Codex를 어디까지 쓸 수 있는지는 요금제가 정합니다. 아래 가격은 확인일(2026년 9월 27일) 기준 공식 요금 페이지의 표시 가격이며 바뀔 수 있습니다.

| 요금제 | Codex에서 되는 것 | 표시 가격 |
|---|---|---|
| Free, Go | 데스크톱 앱에서 GPT-6 Luna. 계정마다 차례로 열립니다 | Free $0, Go 월 $8 |
| Plus | 웹, CLI, IDE 확장, iOS. 자동 코드 리뷰와 Slack 같은 클라우드 연동. GPT-6 Sol과 Luna. 크레딧을 사서 더 쓸 수 있습니다 | 월 $20 |
| Pro | Plus 사용량의 5배 또는 20배 가운데 선택 | 월 $100부터 |
| Business | 데스크톱·모바일 앱, 더 큰 클라우드 환경, SAML SSO와 MFA. 업무 데이터를 기본적으로 학습에 쓰지 않습니다 | 2인 이상, 연간 결제 시 사용자당 월 $20, 월간 결제 시 $25 |
| Enterprise, Edu | Business 기능에 감사 로그, 데이터 보존과 저장 위치 통제 등이 더해집니다 | 영업팀 문의 |

**사용량 한도.** 한도는 5시간 단위로 쓸 수 있는 메시지 수의 범위로 안내되고, 주간 한도가 따로 걸릴 수 있습니다. 내 컴퓨터에서 하는 작업과 클라우드 작업은 같은 한도를 나눠 씁니다. 얼마나 빨리 차는지는 모델, 맥락 크기, 추론 강도에 따라 크게 달라집니다. 예를 들어 Plus에서 5시간 동안 보낼 수 있는 로컬 메시지는 GPT-6 Sol이 15~150개, GPT-6 Luna가 350~3,000개 정도로 안내됩니다. 고정된 수치는 없고 추정치일 뿐입니다. 남은 양은 사용량 대시보드나 CLI의 `/status`, `/usage`로 봅니다. 한도에 닿아도 진행 중이던 응답은 마무리됩니다.

**회사 자료와 계정.** 7단계의 원칙이 여기서도 그대로 적용됩니다. Business 이상 워크스페이스 계정은 업무 데이터를 기본적으로 학습에 쓰지 않습니다. 개인 Plus·Pro 계정은 기본값이 다르므로, 회사 자료를 다루기 전에 설정의 데이터 관련 항목에서 학습 제외 여부를 직접 확인해야 합니다. 메뉴 이름과 위치는 바뀔 수 있으니 화면에서 확인하세요. 가장 안전한 길은 회사가 계약한 워크스페이스 계정으로만 회사 자료를 다루는 것입니다.

**API 키로 쓰는 경우.** 개발팀이 OpenAI API 키를 가지고 있다면 그 키로 Codex에 로그인할 수도 있습니다. 이때는 구독 한도 대신 쓴 만큼 API 요금이 나가고, CLI·IDE 확장·SDK만 쓸 수 있습니다. Codex cloud, GitHub의 `@codex` 리뷰, Slack 연동, 모바일 원격 제어는 API 키 로그인으로는 쓸 수 없습니다. 둘의 차이는 32단계에서 다시 다룹니다.

### Claude와 나란히 놓기

두 회사 도구를 모두 쓰는 조직이라면 대응표를 하나 갖고 있으면 편합니다.

| 하고 싶은 일 | Claude | ChatGPT |
|---|---|---|
| 묻고 답하기 | 채팅 | Chat |
| 결과물 파일까지 맡기기 | Cowork | Work |
| 폴더 속 파일·코드 다루기 | Claude Code | Codex |
| 폴더 규칙 파일 | CLAUDE.md | AGENTS.md(33단계) |
| 클라우드에서 저장소 작업 | Claude Code on the web | Codex cloud |
| PR 검토 부탁 | `@claude` | `@codex review` |

표의 오른쪽 이름은 공식 문서에서 확인한 것입니다. 이름이 같은 층에 놓여 있다고 기능까지 똑같지는 않습니다. 그래도 "지금 하려는 일이 대화인가, 결과물인가, 폴더 작업인가"를 먼저 물으면 어느 도구에서든 들어갈 문을 빨리 찾습니다.

### 현장 장면
누리상사 경영지원팀 오세린 차장은 월요일 아침 대표에게서 짧은 메시지를 받았습니다. "영업본부는 ChatGPT를 계약했고 우리 팀 몇 명은 Claude를 쓰고 있지요. 둘을 어디에 쓰는 게 맞는지 한 장으로 정리해 주세요." 오 차장은 제3부 과정을 마치고 Claude Code로 사내 비품 신청 페이지를 만들어 본 적이 있었지만, ChatGPT는 가끔 메일 문장을 다듬을 때만 열어 봤습니다.

영업본부에서 발급해 준 ChatGPT Business 계정으로 로그인하자 입력창 위에 Chat과 Work가 보였습니다. 오 차장은 먼저 Chat에서 "지난 분기 비품 구매 현황을 3장짜리 발표 자료로 만들어 줘"라고 써 봤습니다. 돌아온 것은 슬라이드별 제목과 요점을 적은 글이었습니다. 같은 요청을 Work로 바꿔 넣자, 대화 옆에 발표 자료 파일이 열렸습니다. 둘째 장의 그래프만 지정해 막대 대신 표로 바꿔 달라고 하니 그 부분만 고쳐졌습니다. "보고서 만들 때는 Work구나." 오 차장은 메모장에 적었습니다.

데스크톱 앱을 열어 보니 ChatGPT와 Codex를 고르는 메뉴가 있었습니다. Codex를 골라 제3부의 방법으로 만들어 쓰던 비품 신청 페이지 폴더를 열어 보려다가 손을 멈췄습니다. 이 폴더는 CLAUDE.md로 규칙을 적어 둔 폴더였습니다. Codex가 이 규칙을 그대로 따를지 알 수 없었습니다. 오 차장은 이 궁금증을 "33단계에서 확인할 것"으로 적어 두었습니다.

마지막으로 걸린 것은 계정이었습니다. 팀원 한 명이 개인 Plus 계정으로 거래처 목록을 정리해 왔다고 말한 것이 떠올랐습니다. 요금 페이지를 보니 Business는 업무 데이터를 기본적으로 학습에 쓰지 않지만, 개인 계정은 사용자가 직접 설정을 확인해야 했습니다. 오 차장은 한 장짜리 정리표 맨 아래에 규칙 하나를 굵게 넣었습니다. "회사 자료는 회사 계정으로만." 그 위에는 세 줄이 올라갔습니다. 묻고 다듬는 일은 Chat 또는 Claude 채팅, 보고서와 발표 자료는 Work 또는 Cowork, 사내 도구와 폴더 작업은 Codex 또는 Claude Code.

### 따라 하기
1. ChatGPT 웹이나 데스크톱 앱에 로그인하고, 입력창 근처에서 Chat과 Work를 바꾸는 전환기를 찾습니다. 성공 기준: 두 방식을 오가며 입력창 모양이나 안내가 바뀌는 것을 봅니다.
2. 가상 자료로 같은 요청("가상의 분기 실적으로 3장짜리 발표 자료를 만들어 줘")을 Chat과 Work에 한 번씩 넣습니다. 성공 기준: Chat은 대화 속 글로, Work는 미리 보고 내려받을 수 있는 파일로 돌아옵니다.
3. 내 계정의 요금제를 확인하고, 위 표에서 Codex를 쓸 수 있는 통로에 표시합니다. 성공 기준: 요금제 이름과 "데스크톱 앱만" 또는 "앱·CLI·IDE·클라우드"처럼 쓸 수 있는 통로를 적어 둡니다.
4. 개인 계정이라면 설정에서 데이터 학습 관련 항목을 찾아 현재 상태를 확인합니다. 회사 계정이라면 관리자에게 워크스페이스 정책을 묻습니다. 성공 기준: 이 계정에 회사 자료를 넣어도 되는지 예·아니오로 답할 수 있습니다.
5. 아래 프롬프트로 내 업무 다섯 가지를 Chat, Work, Codex로 나눠 봅니다. 성공 기준: 다섯 가지 모두 어디로 갈지와 그 이유가 정해졌고, Codex로 간 일이 하나 이상 있습니다.

## 32단계 · Codex 설치와 첫 실행

> 처음에는 데스크톱 앱으로 Codex를 열어 보고, 터미널에서도 쓰려면 CLI를 설치합니다. 로그인은 ChatGPT 계정으로 하고, 켜기 전에 작업 폴더로 들어갑니다.

**걸리는 시간** · 읽기 약 15분 · 따라 하기 약 40분

### 이 단계를 마치면
- 데스크톱 앱에서 Codex를 열고, 운영체제에 맞는 방법으로 Codex CLI를 설치한 뒤 `codex --version`으로 확인할 수 있습니다.
- ChatGPT 계정 로그인과 API 키 로그인의 차이를 설명하고, 알맞은 방식으로 로그인할 수 있습니다.
- 작업 폴더에서 Codex를 켜고, 모델과 추론 강도를 골라 첫 지시를 내릴 수 있습니다.

22단계에서 Claude Code를 설치해 본 분이라면 이번 단계는 훨씬 수월합니다. 공식 문서에서 명령을 복사하고, 설치가 끝나면 버전을 확인하고, 작업 폴더에 들어가서 켜는 순서가 같습니다. 달라지는 것은 두 가지입니다. 하나는 로그인 방식을 고르는 일이고, 다른 하나는 모델과 함께 "추론 강도"를 고르는 일입니다. 둘 다 사용량과 요금에 곧바로 이어지므로 처음에 제대로 알고 넘어가는 편이 좋습니다.

### 두 개의 문: 데스크톱 앱과 CLI

**데스크톱 앱.** 터미널이 아직 낯설다면 앱부터 시작하세요. chatgpt.com/download에서 ChatGPT 데스크톱 앱을 받습니다. Windows는 Microsoft Store에서 설치하거나, PowerShell에서 아래 명령으로 설치할 수도 있습니다.

```powershell
winget install --id 9PLM9XGG6VKS -s msstore
```

앱을 열고 로그인하면 ChatGPT와 Codex 가운데 하나를 고르는 메뉴가 있습니다. Codex를 고르고 작업할 폴더를 엽니다. 실행 위치는 Local, Worktree, Cloud 세 가지인데, 처음에는 Local을 고릅니다. 지금 연 폴더에서 바로 일하는 방식입니다. Worktree는 Git의 워크트리 기능으로 작업 공간을 따로 떼어 일하는 방식이고, Cloud는 클라우드 환경에서 일하는 방식입니다. Free와 Go 요금제는 이 데스크톱 앱에서만 Codex를 쓸 수 있습니다.

**CLI.** 제3부처럼 터미널에서 일하려면 Codex CLI를 설치합니다. 설치 명령은 Codex CLI 공식 문서(learn.chatgpt.com/docs/codex/cli)에서 복사해 붙이세요. 참고로 집필 시점에 안내된 명령은 아래와 같았습니다.

macOS와 Linux의 터미널:

```bash
curl -fsSL https://chatgpt.com/codex/install.sh | sh
```

Windows PowerShell:

```powershell
powershell -ExecutionPolicy ByPass -c "irm https://chatgpt.com/codex/install.ps1 | iex"
```

이미 Node.js를 쓰고 있다면 `npm install -g @openai/codex`로, Mac에서 Homebrew를 쓴다면 `brew install --cask codex`로 설치해도 됩니다. 업데이트는 설치 스크립트를 한 번 더 실행하거나 `brew upgrade --cask codex`를 씁니다.

**Windows 사용자.** 지금의 Codex는 PowerShell에서 바로 돌아가고, Windows 전용 샌드박스를 씁니다. 샌드박스는 Codex가 할 수 있는 일의 범위를 운영체제 차원에서 묶어 두는 장치로, 33단계에서 자세히 다룹니다. Windows 샌드박스에는 `elevated`(권장)와 `unelevated` 두 방식이 있습니다. 관리자 권한이 없는 회사 PC라면 `unelevated`가 대안으로 안내됩니다. 어느 쪽을 쓸지는 IT 담당자와 먼저 이야기하세요. WSL2(Windows 안의 리눅스 환경)에서 쓰는 방법도 있습니다. 이때는 작업 폴더를 `/mnt/c` 아래가 아닌 리눅스 홈 폴더 아래에 두라고 안내합니다. GitHub 저장소의 옛 설치 문서에는 아직 "WSL2로만" 쓴다는 설명이 남아 있으니, 두 안내가 다르면 공식 웹 문서를 따르세요.

**권장 사양.** macOS 12 이상, Ubuntu 20.04 이상, 메모리 4GB 이상(8GB 권장), Git 2.23 이상이 권장됩니다. 21단계에서 설치 전 준비를 마쳤다면 대부분 이미 갖춰져 있습니다.

**설치 확인.** 설치가 끝나면 터미널을 새로 열고 버전을 확인합니다.

```bash
codex --version
```

버전 번호가 나오면 설치가 끝난 것입니다. 무언가 이상하면 `codex doctor`를 실행해 보세요. 설치, 설정, 인증 상태를 진단한 보고서가 나옵니다. 오류가 있으면 그 보고서를 통째로 복사해 두는 것이 다음 걸음입니다.

### 로그인: ChatGPT 계정과 API 키

Codex에 로그인하는 방법은 두 가지입니다.

| 로그인 방식 | 요금 | 쓸 수 있는 곳 | 안 되는 것 |
|---|---|---|---|
| ChatGPT 계정 | 구독 요금제의 사용량 한도 안에서 씁니다 | 데스크톱 앱, CLI, IDE 확장, Codex cloud | 요금제에 없는 기능 |
| API 키 | 쓴 만큼 API 요금이 나갑니다 | CLI, IDE 확장, SDK 같은 로컬 도구 | Codex cloud, GitHub `@codex` 리뷰, Slack·Linear 연동, 모바일 원격 제어 |

이 책의 독자라면 ChatGPT 계정 로그인이 기본입니다. 회사가 계약한 Business나 Enterprise 계정이 있다면 반드시 그 계정으로 들어가세요. 개발팀에서 "우리 API 키 쓰세요"라고 건네줄 때가 있는데, 그러면 사용 요금이 개발팀 API 계정으로 청구되고 클라우드 기능은 쓰지 못합니다.

CLI에서 쓰는 로그인 명령은 네 가지면 충분합니다.

| 명령 | 하는 일 |
|---|---|
| `codex login` | 브라우저를 열어 ChatGPT 계정으로 로그인합니다 |
| `codex login status` | 지금 어떤 방식으로 로그인돼 있는지 보여 줍니다 |
| `codex logout` | 로그아웃합니다 |
| `codex login --device-auth` | 브라우저가 없는 원격 서버 같은 곳에서 기기 코드로 로그인합니다(베타) |

로그인 정보는 내 홈 폴더의 `.codex` 폴더 안 `auth.json` 파일이나 운영체제의 자격 증명 저장소에 저장됩니다. `auth.json`은 비밀번호처럼 다뤄야 합니다. 공유 드라이브나 저장소에 올리지 말고, 다른 사람에게 보내지 마세요. CLI와 IDE 확장은 이 로그인 정보를 함께 씁니다. 이메일과 비밀번호로 가입한 계정은 Codex cloud를 쓰기 전에 2단계 인증(MFA)을 켜야 합니다.

### 첫 폴더 열기

첫 실행 순서는 22단계와 같습니다. 작업 폴더로 먼저 들어간 뒤 켭니다.

```bash
cd ~/work/nuri-supplies
codex
```

처음 켜면 로그인 방법을 묻습니다. **Sign in with ChatGPT**를 고르면 브라우저가 열리고, 로그인을 마치면 터미널로 돌아옵니다. 그다음 Codex는 이 폴더에서 얼마만큼 알아서 일해도 되는지 제안합니다. 폴더가 Git으로 관리되고 있으면 Auto를, 아니면 읽기 전용(read-only)을 권합니다. Auto는 폴더 안에서는 읽기·수정·명령 실행을 알아서 하고, 폴더 밖을 고치거나 인터넷을 쓰려 할 때만 묻는 방식입니다. 읽기 전용은 이름 그대로 읽기만 합니다. 이 차이가 곧 Git 체크포인트가 중요한 이유입니다. 되돌릴 기록이 있어야 알아서 고치게 둘 수 있기 때문입니다. 공식 문서도 작업 전후로 커밋을 남기라고 권합니다. 연습용 폴더라면 25·26단계에서 본 기록 장치 켜기(git 초기화)와 첫 커밋을 Codex를 켜기 전에 먼저 해 두세요. 제3부에서는 이 일을 Claude Code에게 시켰지만, 여기서는 터미널에서 직접 쳐도 세 줄이면 됩니다. 빈 폴더라면 메모 파일 하나(예: README.md)를 먼저 넣어야 첫 커밋이 만들어집니다.

```bash
git init
git add .
git commit -m "작업 시작 전 상태"
```

권한은 33단계에서 자세히 다룹니다.

첫 지시는 가볍게 합니다. "이 폴더에 무엇이 있는지 알려 줘." 폴더 안 파일 목록이 돌아오면 Codex가 제대로 된 폴더에 들어와 있는 것입니다. 이어서 `/status`를 입력해 보세요. 지금 쓰는 모델, 승인 정책, 쓰기가 허용된 폴더, 남은 맥락, 사용량이 한 화면에 나옵니다. 앞으로 무언가 이상하다 싶을 때 가장 먼저 칠 명령입니다. 끝낼 때는 `/quit` 또는 `/exit`를 입력합니다. 터미널에서 하던 대화를 앱 화면으로 보고 싶으면 `/app`을 입력합니다.

### 모델과 추론 강도 고르기

Codex에서는 모델과 추론 강도를 따로 고릅니다. 집필 시점 기준으로 고를 수 있는 주요 모델은 셋입니다.

| 모델 | 이런 일에 | 처음 권장 추론 강도 |
|---|---|---|
| GPT-6 Sol | 일상 작업과 복잡한 코딩. 현재 권장 모델입니다 | Medium |
| GPT-6 Luna | 할 일이 분명하고 반복적인 작업, 대량 처리 | High |
| GPT-6 Astra | 가장 어렵고 오래 걸리는 작업 | Light |

추론 강도는 모델이 답하기 전에 얼마나 오래 따져 보는지를 정합니다. 화면에는 Light, Medium, High, Extra High, Max, Ultra로 나옵니다(CLI에서는 Light가 Low로 표시됩니다). 모델마다 지원하는 범위가 달라서, GPT-6 Luna는 Max까지만 되고 Ultra는 고를 수 없습니다. Ultra는 일을 여러 서브에이전트로 나눠 동시에 처리하는 방식입니다.

CLI에서는 `/model`을 입력해 모델과 추론 강도를 함께 고릅니다. 켤 때부터 모델을 정하려면 `codex -m gpt-6-sol`처럼 씁니다. 데스크톱 앱에서는 입력창 아래의 모델 메뉴에서 고릅니다.

어떻게 고를까요? 원칙은 단순합니다. 처음에는 권장값으로 시작하고, 답이 얕다고 느껴질 때만 한 단계씩 올립니다. 강도를 올릴수록 답은 느려지고 사용량은 빨리 찹니다. 31단계에서 본 것처럼 같은 Plus 요금제라도 모델에 따라 5시간에 보낼 수 있는 메시지 수가 열 배 넘게 차이 납니다. 파일 이름 바꾸기처럼 규칙이 분명한 일은 Luna로, 여러 파일에 걸친 수정은 Sol로, 정말 막힌 문제만 Astra로 보내는 식으로 나눠 쓰면 한도를 아낄 수 있습니다. 모델 이름은 몇 주 사이에도 바뀌고 있으니 `/model` 목록이 이 표와 다르면 화면이 맞습니다.

### 현장 장면
오세린 차장의 노트북은 Windows였습니다. IT팀 하준영 대리에게 먼저 연락해 설치 허락을 받았고, 하 대리는 관리자 권한은 줄 수 없으니 샌드박스는 `unelevated`로 쓰라고 알려 주었습니다. 오 차장은 Microsoft Store에서 ChatGPT 데스크톱 앱을 설치해 Codex 화면을 열어 본 뒤, 공식 문서에서 PowerShell 설치 명령을 복사해 CLI까지 설치했습니다. 새 창에서 `codex --version`을 치자 버전 번호가 나왔습니다.

첫 번째 걸림돌은 로그인이었습니다. 옆자리 개발팀 동료가 "우리 팀 API 키 있어요"라며 키를 알려 주었고, 오 차장은 별생각 없이 그 키로 로그인했습니다. 일은 잘됐습니다. 그런데 오후에 Codex cloud를 열어 보려 하자 쓸 수 없다는 안내가 나왔습니다. `codex login status`를 쳐 보니 API 키로 로그인돼 있었습니다. 게다가 오전에 쓴 양은 개발팀 API 요금으로 청구될 참이었습니다. 오 차장은 `codex logout`으로 나온 뒤 `codex login`으로 회사 Business 계정에 다시 들어갔고, 동료에게는 키를 쓴 사실을 알렸습니다.

두 번째 걸림돌은 폴더였습니다. 새로 만든 `C:\work\nuri-supplies` 폴더에서 Codex를 켜자 읽기 전용으로 시작하라는 제안이 나왔습니다. 그대로 두고 "비품 목록 파일을 하나 만들어 줘"라고 하자 Codex는 파일을 쓰려면 허락이 필요하다고 물었습니다. 폴더가 Git으로 관리되지 않았기 때문이었습니다. 오 차장은 Codex를 끝내고 메모 파일 하나를 넣은 뒤, 터미널에서 git 초기화와 첫 커밋을 직접 하고 다시 켰습니다. 이번에는 Auto를 권했습니다.

마지막은 모델이었습니다. 호기심에 `/model`에서 가장 높은 추론 강도를 골라 "이 폴더에 무엇이 있는지 알려 줘"라고 물었더니, 답은 한참 뒤에야 나왔고 `/status`의 사용량이 눈에 띄게 올라가 있었습니다. 오 차장은 GPT-6 Sol과 Medium으로 되돌렸습니다. 폴더 목록 하나 보는 데 깊은 생각은 필요 없었습니다.

### 따라 하기
1. chatgpt.com/download에서 ChatGPT 데스크톱 앱을 설치하고 로그인한 뒤 Codex를 고릅니다. 성공 기준: Codex 화면에서 폴더를 열 수 있고, 실행 위치 Local이 보입니다.

3. `codex login`으로 ChatGPT 계정에 로그인하고 `codex login status`로 확인합니다. 성공 기준: API 키가 아닌 ChatGPT 계정으로 로그인돼 있다고 나옵니다.

6. `/model`로 GPT-6 Sol과 Medium을 고른 뒤 `/quit`로 끝냅니다. 성공 기준: 다시 켰을 때 고른 모델로 시작하는지 `/status`로 확인합니다.

## 33단계 · AGENTS.md와 권한: 승인 방식과 샌드박스

> Codex는 일을 시작하기 전에 AGENTS.md를 읽고, 샌드박스와 승인 정책이라는 두 겹의 울타리 안에서 움직입니다. 울타리를 넓히기 전에 되돌릴 체크포인트부터 만듭니다.

**걸리는 시간** · 읽기 약 20분 · 따라 하기 약 45분

### 이 단계를 마치면
- AGENTS.md를 알맞은 위치에 두고, 여러 단계의 파일이 어떻게 합쳐지는지 설명할 수 있습니다.
- 샌드박스 모드와 승인 정책의 이름과 뜻을 구분하고, 작업에 맞는 조합을 고를 수 있습니다.
- Codex가 한 일을 변경 내역으로 확인하고 Git 체크포인트로 되돌릴 수 있습니다.

23단계에서 여러분은 CLAUDE.md에 규칙을 적고, 28단계에서 무엇을 묻지 않고 허락할지 정리했습니다. Codex에도 같은 두 장치가 있습니다. 규칙은 AGENTS.md에 적고, 권한은 샌드박스와 승인 정책으로 정합니다. 이름과 설정 방식이 달라서 처음에는 헷갈리지만, 뜻을 한 번 잡아 두면 Claude Code에서 쓰던 감각이 그대로 통합니다.

### AGENTS.md: 어디에 두고 어떻게 합쳐지나

Codex는 작업을 시작하기 전에 `AGENTS.md`를 읽습니다. CLAUDE.md처럼 마크다운으로 쓴 지침 파일입니다. 두는 곳은 세 층입니다.

| 층 | 위치 | 이런 내용을 적습니다 |
|---|---|---|
| 전역 | 내 홈 폴더의 `.codex/AGENTS.md` | 모든 폴더에 통하는 내 습관. 예: "답은 우리말로" |
| 프로젝트 | 작업 폴더 맨 위(보통 Git 저장소의 가장 위 폴더) | 이 폴더가 무엇을 하는 곳인지, 지킬 규칙, 하지 말 것 |
| 하위 폴더 | 작업 폴더 안의 특정 하위 폴더 | 그 폴더에만 해당하는 규칙. 예: "이 폴더의 파일은 읽기만 한다" |

읽는 순서는 이렇습니다. 먼저 전역 파일을 읽고, 이어서 저장소 맨 위 폴더부터 지금 Codex를 켠 폴더까지 한 층씩 내려가며 폴더마다 파일 하나씩을 읽습니다. 읽은 내용은 위쪽부터 차례로 이어 붙입니다. 그래서 지금 폴더에 가까운 파일이 뒤에 붙고, 앞의 내용과 부딪히면 뒤의 것이 앞섭니다. 폴더마다 `AGENTS.override.md`가 있으면 그 폴더에서는 AGENTS.md 대신 그것을 읽습니다. 잠깐 규칙을 바꿔 시험할 때 원래 파일을 건드리지 않고 쓰는 방법입니다. 빈 파일은 건너뛰고, 합친 크기가 기본 32KiB에 닿으면 그 뒤로는 더 읽지 않습니다. 규칙이 길어지면 뒤쪽 규칙이 통째로 빠질 수 있다는 뜻이니 짧게 유지하세요.

처음부터 직접 쓸 필요는 없습니다. Codex 입력창에 `/init`을 치면 지금 폴더를 훑어보고 AGENTS.md 초안을 만들어 줍니다. 초안은 대개 기술 설명 위주이므로, 23단계에서 했던 것처럼 우리 팀의 말로 규칙과 금지 사항을 보탭니다. 흐린 말 대신 확인할 수 있는 문장으로 쓰는 원칙도 같습니다. 공식 문서가 예로 드는 규칙도 모두 확인할 수 있는 문장입니다. "파일을 고친 뒤에는 테스트 명령을 실행한다", "새 도구를 추가하기 전에 확인을 받는다" 같은 식입니다. GitHub에서 `@codex review`를 쓸 때 적용할 검토 규칙은 `## Code Review Rules`라는 제목 아래에 적습니다. 비밀번호나 인증키는 절대 적지 않습니다. AGENTS.md도 저장소에 함께 올라가 다른 사람이 읽는 파일입니다.

```markdown
# 비품 신청 페이지

## 이 폴더는
경영지원팀이 쓰는 사내 비품 신청 페이지다. 직원들이 휴대폰으로 연다.

## 규칙
- 화면 문구는 모두 우리말로 쓴다.
- 신청자는 부서명만 보여 주고 이름은 보여 주지 않는다.
- 파일은 index.html 하나로 유지한다.

## 하지 말 것
- 새 도구나 패키지를 설치하기 전에 반드시 묻는다.
- 파일을 지우기 전에 반드시 묻는다.
- 인증키나 비밀번호를 파일에 적지 않는다.

## 끝났다고 말하기 전에
- 브라우저로 열어 신청 목록이 보이는지 확인하고, 확인한 방법을 적는다.
```

**CLAUDE.md와 같이 두기.** 한 폴더를 Claude Code와 Codex가 함께 쓰는 팀이 늘고 있습니다. 여기서 알아 둘 사실이 있습니다. Codex는 CLAUDE.md를 저절로 읽지 않습니다. 기본으로 찾는 이름은 AGENTS.override.md와 AGENTS.md뿐입니다. 방법은 세 가지입니다.

| 방법 | 어떻게 | 알아 둘 점 |
|---|---|---|
| 두 파일에 같은 규칙 | CLAUDE.md와 AGENTS.md에 같은 내용을 적습니다 | 가장 단순합니다. 규칙을 고칠 때 두 파일을 함께 고쳐야 합니다 |
| 대체 파일명 설정 | Codex 설정(`config.toml`)의 `project_doc_fallback_filenames`에 `CLAUDE.md`를 넣습니다 | 공식 문서에 있는 설정입니다. 실제로 읽히는지는 "지금 따르는 규칙을 요약해 줘"라고 물어 직접 확인하세요 |
| 가져오기 | Codex에서 `/import`로 Claude Code의 설정을 가져옵니다 | 가져와도 Claude Code 쪽 설정은 바뀌지 않습니다 |

어느 방법이든 끝은 같습니다. Codex를 켜고 "지금 따르고 있는 규칙을 요약해 줘"라고 물어, 적어 둔 규칙이 돌아오는지 봅니다.

### 두 겹의 울타리: 샌드박스와 승인 정책

Codex의 권한은 두 층으로 되어 있습니다. **샌드박스**는 기술적으로 무엇을 할 수 있는지를 정합니다. **승인 정책**은 언제 멈추고 나에게 물을지를 정합니다. 28단계에서 Claude Code의 허락 규칙을 정리했던 일을 Codex에서는 이 두 층으로 나눠서 합니다.

샌드박스 모드(설정 이름 `sandbox_mode`, 실행할 때는 `--sandbox`)는 세 가지입니다.

| 값 | 뜻 |
|---|---|
| `read-only` | 읽기만 합니다 |
| `workspace-write` | 작업 폴더(와 임시 폴더) 안에서만 파일을 씁니다. 인터넷은 기본으로 꺼져 있습니다 |
| `danger-full-access` | 샌드박스가 없습니다. 무엇이든 할 수 있습니다 |

승인 정책(설정 이름 `approval_policy`, 실행할 때는 `--ask-for-approval` 또는 `-a`)은 이렇습니다.

| 값 | 뜻 |
|---|---|
| `on-request` | 샌드박스 안의 일은 묻지 않고 하고, 밖으로 나가야 할 때 묻습니다. 대화형으로 쓸 때의 기본값입니다 |
| `never` | 묻지 않습니다. 사람이 지켜보지 않는 자동 실행용입니다. 샌드박스의 제한은 그대로 남습니다 |
| `granular` | 항목별로 물을지, 자동으로 거절할지를 따로 정합니다 |

예전 자료에는 `untrusted`와 `on-failure`라는 값도 나옵니다. `untrusted`는 지원이 끝나 설정에 남아 있으면 실행이 안 될 수 있고, `on-failure`는 곧 없어질 값입니다. 인터넷에서 찾은 설정 예시에 이 두 값이 있으면 쓰지 마세요.

대표 조합은 두 가지만 기억하면 됩니다.

| 이름 | 조합 | 이럴 때 |
|---|---|---|
| Auto | `--sandbox workspace-write --ask-for-approval on-request` | 평소 작업. 폴더 안에서는 알아서 읽고 고치고 명령을 실행하고, 폴더 밖 수정이나 인터넷 사용은 묻습니다 |
| 읽기 전용 | `--sandbox read-only --ask-for-approval on-request` | 처음 보는 폴더를 살필 때, 원본 자료만 읽힐 때 |

대화 중에 바꾸려면 CLI에서 `/permissions`를 입력하고 Auto와 Read Only 가운데 고릅니다. 지금 상태는 `/status`로 확인합니다. 늘 같은 조합을 쓰고 싶으면 설정 파일 `config.toml`에 적어 둡니다. 내 홈 폴더의 `.codex/config.toml`은 모든 폴더에, 작업 폴더 안의 `.codex/config.toml`은 그 폴더에만 적용됩니다. 작업 폴더의 설정은 내가 신뢰한다고 표시한 폴더에서만 읽힙니다. CLI, IDE 확장, 데스크톱 앱이 같은 설정을 함께 씁니다.

```toml
approval_policy = "on-request"
sandbox_mode = "workspace-write"
```

모든 제한을 없애는 `--dangerously-bypass-approvals-and-sandbox`(별칭 `--yolo`)도 있습니다. 공식 문서도 권하지 않습니다. 이름에 "위험하다"가 붙은 옵션은 쓰지 않는다고 정해 두세요. 회사 차원에서는 관리자가 `requirements.toml`로 이런 설정을 아예 금지할 수 있습니다.

`workspace-write`에서도 손대지 못하는 곳이 있습니다. 작업 폴더 안의 `.git`, `.agents`, `.codex` 폴더는 읽기 전용으로 보호됩니다. Git 기록과 Codex 설정을 Codex가 스스로 고치지 못하게 막아 두는 장치입니다.

### 앱의 권한 모드, 자동 검토, 네트워크

데스크톱 앱과 IDE 확장에서는 같은 내용을 세 가지 권한 모드로 고릅니다.

| 앱의 권한 모드 | 뜻 |
|---|---|
| Ask for approval | 기본값입니다. 필요할 때 나에게 묻습니다 |
| Approve for me | 승인 요청을 사람 대신 검토 에이전트가 판단합니다. 설정 화면에서는 Auto-review라는 이름으로 나옵니다 |
| Full access | 제한 없이 실행합니다 |

뒤의 두 모드는 설정의 권한 항목(General 아래 Permissions)에서 켜야 메뉴에 나타납니다. 화면 이름과 위치는 바뀔 수 있으니 앱에서 확인하세요. Approve for me(자동 검토)를 켜도 샌드박스 범위는 넓어지지 않습니다. 묻는 상대가 사람에서 검토 에이전트로 바뀔 뿐입니다. 검토 에이전트가 거절한 동작을 한 번만 다시 허용하려면 CLI에서 `/approve`를 씁니다. 처음 몇 주는 Ask for approval로 두고, 어떤 요청이 오는지 읽어 보는 편이 배우기에 좋습니다.

**네트워크 기본값.** 내 컴퓨터에서 `workspace-write`로 일할 때 인터넷은 꺼져 있습니다. Codex가 무언가를 내려받거나 설치하려 하면 승인 요청이 옵니다. 늘 켜 두려면 설정의 `[sandbox_workspace_write]` 아래 `network_access = true`를 적지만, 회사 PC에서는 꺼 둔 채 요청이 올 때마다 읽고 판단하는 편이 안전합니다. 웹 검색은 기본값이 OpenAI가 미리 색인해 둔 결과를 쓰는 `cached`이고, 실시간 검색은 따로 켜야 합니다. 클라우드 작업도 에이전트가 일하는 동안에는 인터넷이 기본으로 막혀 있습니다.

### 되돌리기는 Git 체크포인트로

Claude Code에는 대화와 파일을 앞 시점으로 돌리는 기능이 있었습니다. Codex CLI에는 그런 되돌리기 명령이 없습니다. 명령 목록에 `/undo`도 없습니다. 공식 문서가 권하는 방법은 Git 체크포인트입니다. 맡기기 전에 커밋하고, 끝나면 확인한 뒤 다시 커밋합니다. `git status`가 깨끗한 상태에서 맡기라는 것도 같은 이유입니다. 26단계에서 익힌 커밋과 되돌리기가 여기서 안전장치 노릇을 합니다.

Codex 안에서 쓰는 확인 도구는 두 가지입니다. `/diff`는 지금까지 바뀐 내용을 보여 줍니다. Git이 아직 추적하지 않는 새 파일도 포함합니다. `/review`는 작업 중인 변경을 검토해 줍니다. 데스크톱 앱의 리뷰 화면에서는 바뀐 내용을 전체, 파일, 덩어리 단위로 골라 되돌릴(Revert) 수 있습니다. 마음에 들지 않는 변경은 이 화면이나 26단계의 Git 명령으로 되돌리고, 확인이 끝난 변경만 커밋합니다.

### 현장 장면
오세린 차장은 Claude Code로 만들었던 비품 신청 페이지 폴더를 Codex로 열었습니다. 31단계에서 적어 둔 궁금증부터 풀었습니다. "지금 따르고 있는 규칙을 요약해 줘." Codex는 폴더 구조만 설명할 뿐, CLAUDE.md에 적은 "신청자는 부서명만 보여 준다"는 규칙은 말하지 않았습니다. 오 차장은 `/init`으로 AGENTS.md 초안을 받고, CLAUDE.md의 규칙과 하지 말 것을 그대로 옮겨 적었습니다. 두 파일 맨 위에는 "규칙을 고치면 CLAUDE.md와 AGENTS.md를 함께 고친다"는 문장을 넣었습니다. 같은 질문을 다시 하자 이번에는 부서명 규칙이 돌아왔습니다.

다음으로 신청 목록에 날짜 정렬 기능을 붙여 달라고 했습니다. 맡기기 전에 `git status`가 깨끗한지 보고 커밋부터 했습니다. 작업 도중 승인 요청이 하나 왔습니다. 날짜를 다루는 도구를 인터넷에서 받아 설치하겠다는 내용이었습니다. AGENTS.md에 "새 도구를 설치하기 전에 반드시 묻는다"고 적어 둔 대로였습니다. 오 차장은 거절하고, 설치 없이 할 수 있는 방법으로 해 달라고 했습니다. Codex는 페이지 안에서 직접 정렬하는 방식으로 바꿔 끝냈습니다.

결과를 브라우저로 열어 보니 정렬은 됐지만 휴대폰 폭에서 표가 옆으로 밀려 있었습니다. `/diff`로 보니 정렬 말고도 표 스타일이 함께 바뀌어 있었습니다. 오 차장은 데스크톱 앱의 리뷰 화면에서 스타일이 바뀐 덩어리만 되돌리고 정렬 부분은 남겼습니다. 다시 열어 보니 표도 제자리였습니다. 그제야 커밋했습니다.

그날 저녁 영업본부의 동료 하나가 "매번 묻는 거 귀찮으니 Full access로 켜 두면 편하다"고 조언했습니다. 오 차장은 고맙다고만 하고 설정을 그대로 두었습니다. 오늘 거절한 설치 요청 하나가 그 이유였습니다.

### 따라 하기
1. 작업 폴더에서 `git status`를 확인하고, 깨끗하지 않으면 커밋부터 합니다. 성공 기준: `git status`에 바뀐 파일이 없습니다.
2. Codex를 켜고 `/init`으로 AGENTS.md 초안을 받은 뒤, "이 폴더는", "규칙", "하지 말 것", "끝났다고 말하기 전에"를 채웁니다. 성공 기준: 모든 규칙이 확인할 수 있는 문장이고, 비밀 값이 없습니다.
3. CLAUDE.md가 있는 폴더라면 위 세 방법 가운데 하나를 골라 적용합니다. 성공 기준: "지금 따르고 있는 규칙을 요약해 줘"에 두 파일의 핵심 규칙이 모두 돌아옵니다.
4. `/status`로 지금 샌드박스와 승인 정책을 확인하고, `/permissions`에서 Read Only와 Auto를 한 번씩 바꿔 봅니다. 성공 기준: 바꿀 때마다 `/status`의 표시가 달라집니다.
5. Auto 상태에서 작은 수정 하나를 맡기고, 끝나면 `/diff`로 바뀐 내용을 봅니다. 성공 기준: 바뀐 파일 목록을 말할 수 있고, 시키지 않은 변경이 있으면 찾아냅니다.
6. 마음에 들지 않는 변경 하나를 앱의 리뷰 화면이나 Git으로 되돌린 뒤, 나머지를 커밋합니다. 성공 기준: 되돌린 부분만 원래대로 돌아오고 `git log`에 새 커밋이 보입니다.

### 스스로 점검

- [ ] 샌드박스 모드와 승인 정책이 각각 무엇을 정하는지 구분하고, Auto가 어떤 조합인지 말할 수 있습니까?
- [ ] 맡기기 전에 커밋하고, 끝난 뒤 `/diff`로 확인하고, 필요 없는 변경을 되돌려 봤습니까?

### 기억할 것
- AGENTS.md는 전역, 저장소 맨 위, 하위 폴더 순으로 이어 붙고 가까운 파일이 앞섭니다. Codex는 CLAUDE.md를 저절로 읽지 않습니다.
- 샌드박스는 할 수 있는 범위를, 승인 정책은 묻는 시점을 정합니다. 평소에는 Auto(`workspace-write` + `on-request`), 처음 보는 폴더는 읽기 전용입니다.
- 되돌리기는 Git 체크포인트로 합니다. 맡기기 전에 커밋하고, `/diff`로 확인한 변경만 남깁니다.

## 34단계 · 코딩 없이 쓰는 Codex

> Codex는 폴더 속 파일을 규칙대로 다루는 데도 쓸모가 있습니다. 원본은 복사본으로 가져와 커밋해 두고, 결과는 건수와 변경 내역으로 확인합니다.

**걸리는 시간** · 읽기 약 10분 · 따라 하기 약 60분

### 이 단계를 마치면
- 폴더 정리, 파일 합치기, 보고서 초안처럼 코드 없는 일을 Codex에 로컬로 맡길 수 있습니다.
- 원본을 복사본으로 가져오고 Git 커밋과 읽기 전용 모드로 보호할 수 있습니다.
- 받은 결과를 건수, 합계, 변경 내역으로 확인할 수 있습니다.

24단계에서 Claude Code로 지점별 파일을 합치고 보고서 초안을 받았습니다. 같은 일을 Codex로도 할 수 있습니다. 31단계에서 본 것처럼 공식 안내는 개발이 아닌 업무에 Work를 권합니다. 파일 몇 개를 첨부해 보고서 한 편을 받는 일이라면 Work가 더 간편합니다. 그런데 이런 경우에는 Codex가 잘 맞습니다.

| 이런 일 | Codex가 맞는 까닭 |
|---|---|
| 폴더 하나에 파일이 수십, 수백 개 있습니다 | 첨부할 필요 없이 폴더 전체를 작업 범위로 삼습니다 |
| 같은 규칙을 매달 되풀이합니다 | 규칙을 AGENTS.md에 적어 두면 다음 달에도 그대로 따릅니다 |
| 무엇이 바뀌었는지 기록으로 남겨야 합니다 | Git 커밋과 `/diff`로 바뀐 파일과 내용을 확인합니다 |
| 원본이 절대 바뀌면 안 됩니다 | 읽기 전용 모드와 커밋으로 원본이 그대로인지 확인할 수 있습니다 |

어떤 일을 맡길 수 있는지는 24단계의 세 갈래와 같습니다. 읽고 합치기, 초안 만들기, 반복 파일 작업입니다. 이 단계에서는 Codex에서 달라지는 점만 모아 봅니다.

### 원본은 복사본으로, 그리고 커밋

24단계의 원칙은 그대로입니다. 원본·작업·결과 폴더를 나누고, 원본 폴더에는 받은 파일의 복사본만 넣고, 원본은 읽기만 하게 합니다. 개인정보나 기밀 열은 넣기 전에 사람이 직접 지웁니다. Codex가 읽은 파일 내용은 답을 만들기 위해 모델로 전달되기 때문에, "개인정보 열은 지워 줘"라는 부탁은 이미 늦습니다. 7단계의 원칙입니다.

Codex에서는 여기에 두 가지를 더합니다.

**첫째, 원본을 넣은 직후에 커밋합니다.** 업무 폴더에도 32단계에서 본 세 줄(`git init`, `git add .`, `git commit`)로 기록을 켜 두면 원본 파일이 조금이라도 바뀌었을 때 `git status`와 `/diff`에 곧바로 드러납니다. 24단계에서 "업무 파일에는 되돌릴 기록이 없다"고 했던 약점을 Codex에서는 Git으로 메울 수 있습니다. 이 폴더는 GitHub에 올리지 않습니다. 기록은 내 컴퓨터에만 둡니다. 커밋은 터미널에서 직접 하는 편이 간단합니다. `workspace-write`에서도 `.git` 폴더는 보호되므로, Codex에게 커밋을 시키면 승인 요청이 올 수 있습니다.

**둘째, 살필 때는 읽기 전용으로 켭니다.** 처음 폴더를 훑어보고 대응표를 받는 동안은 아무것도 고칠 필요가 없습니다.

```bash
codex --sandbox read-only --ask-for-approval on-request
```

대응표를 확인하고 실제로 합칠 때가 되면 `/permissions`로 Auto로 바꿉니다. `workspace-write`는 작업 폴더 안에서만 쓰므로, 폴더 밖의 파일은 허락 없이 건드리지 못합니다. 다만 원본 폴더도 작업 폴더 안에 있으니 쓰기가 막히지는 않습니다. 원본은 AGENTS.md의 규칙과 커밋으로 지킵니다.

```markdown
## 규칙
- 원본 폴더의 파일은 읽기만 한다. 고치거나 지우거나 이름을 바꾸지 않는다.
- 새 파일은 작업 폴더나 결과 폴더에 만든다.
- 파일을 지우거나 덮어쓰기 전에는 반드시 묻는다.
- 새 도구를 설치하기 전에 반드시 묻는다.
```

**엑셀 파일은 CSV로.** Codex가 엑셀 파일을 읽으려고 도구를 설치하겠다고 할 수 있습니다. 인터넷이 기본으로 꺼져 있으니 승인 요청이 오고, 회사 PC에서는 설치가 막히기도 합니다. 이럴 때는 24단계와 같이 엑셀에서 CSV(UTF-8)로 저장해 넣는 것이 가장 빠릅니다.

### 폴더 정리와 파일 합치기

**폴더 정리.** 파일 이름을 규칙에 맞추거나 종류별로 하위 폴더에 나누는 일은 Codex가 명령 몇 개로 끝냅니다. 속도가 빠른 만큼 순서를 지킵니다. 먼저 "바꾸기 전 이름과 바꾼 뒤 이름"을 표로 받고, 원본을 건드리지 않도록 결과 폴더에 복사해서 이름을 바꾸게 하고, 열 개쯤 먼저 해 본 뒤 나머지를 맡깁니다. 끝나면 `/diff`나 `git status`로 원본 폴더에 변화가 없는지 봅니다.

**파일 합치기.** 합치기 전에 대응표를 먼저 받는 순서도 24단계와 같습니다. 파일마다 어떤 항목이 있고, 이름이 다른 항목 가운데 어느 것을 같은 것으로 볼지, 날짜와 금액 형식을 어떻게 맞출지를 표로 받아 내가 고친 뒤에 합칩니다. 할 일이 분명하고 파일이 많으면 32단계에서 본 것처럼 GPT-6 Luna가 한도를 아끼기에 좋습니다. 대응표를 짜는 판단이 까다로우면 GPT-6 Sol로 대응표를 받고, 실제 합치기는 Luna로 넘기는 식으로 나눠 쓸 수도 있습니다.

### 보고서 초안과 결과 확인

보고서 초안은 합친 표에서만 받습니다. 숫자는 표에 있는 것만 쓰게 하고, 계산한 값에는 계산식을 붙이고, 해석이나 원인 추정은 [짐작]으로 표시하게 합니다. 보고서 파일을 Codex로 만들 수도 있지만, 발표 자료처럼 모양이 중요한 결과물이라면 합친 표를 Work에 넘겨 파일로 만드는 편이 편할 수 있습니다. 한 일에 두 도구를 이어 쓰는 방식입니다.

결과 확인은 30단계의 원칙을 따릅니다. "다 됐습니다"라는 말을 믿지 않고 직접 봅니다. Codex에서는 확인 수단이 하나 더 있습니다.

| 확인 | 방법 |
|---|---|
| 건수 | 원본 파일별 줄 수의 합과 합친 표의 줄 수가 같은지 봅니다 |
| 합계 | 원본 하나를 직접 열어 합계를 보고, 합친 표의 같은 부분과 비교합니다 |
| 빈 값 | 합친 표에서 비어 있는 값이 몇 개이고 어느 원본에서 왔는지 목록으로 받습니다 |
| 변경 내역 | `git status`와 `/diff`로 원본 폴더에 바뀐 파일이 하나도 없는지 봅니다 |

건수와 빈 값은 Codex에 시켜도 되지만, 합계 하나는 반드시 내 눈으로 원본을 열어 비교합니다. 합친 쪽과 검산한 쪽이 같으면 같은 실수를 두 번 할 뿐입니다. 확인이 끝나면 결과 폴더를 커밋해 둡니다. 다음 달에 같은 일을 할 때 이번 결과와 비교할 기준이 됩니다.

### 현장 장면
가람시 민원여권과 배수민 주무관은 매달 초 읍면동 열네 곳에서 올라온 민원 처리 현황을 한 표로 합쳐 과장에게 올립니다. 파일 형식은 제각각이었습니다. 어떤 동은 엑셀로, 어떤 면은 CSV로 보냈고, 파일 이름도 "9월현황", "민원_0930", "현황표(최종)"처럼 뒤죽박죽이었습니다. 시청은 ChatGPT Business를 도입했고, 배 주무관은 제3부 과정을 마친 뒤 Codex를 설치해 두었습니다.

배 주무관은 `C:\work\minwon-2609` 폴더를 만들고 원본·작업·결과 하위 폴더를 나눴습니다. 공유 폴더에서 파일 열네 개를 복사해 오기 전에, 민원인 이름과 연락처 열을 엑셀에서 직접 지운 사본부터 만들었습니다. 엑셀 파일 다섯 개는 CSV(UTF-8)로 다시 저장했습니다. 그다음 `git init`을 하고 원본을 넣은 채로 첫 커밋을 했습니다. AGENTS.md에는 원본 보호 규칙 네 가지를 적었습니다.

Codex는 읽기 전용으로 켰습니다. 파일 이름을 "읍면동명_2026-09.csv"로 맞추는 미리보기 표를 받아 보니, "현황표(최종)"이 어느 동의 파일인지 Codex도 알지 못해 "확인 필요"로 표시해 두었습니다. 배 주무관이 파일을 열어 보니 산내면 것이었습니다. 이어 대응표를 받았습니다. 두 곳은 "처리완료"와 "완료"를 섞어 썼고, 한 곳은 날짜를 "9.3." 형식으로 적었습니다. 배 주무관은 상태 값을 "완료, 처리중, 이관" 세 가지로 맞추고 날짜는 2026-09-03 형식으로 통일하라고 고쳐 적었습니다.

`/permissions`로 Auto로 바꾼 뒤 이름 바꾼 사본은 작업 폴더에, 합친 표는 결과 폴더에 만들게 했습니다. "총 1,286건을 합쳤습니다." 배 주무관은 건수 검산을 시켰습니다. 원본 줄 수를 더하니 1,302건이었습니다. 차이 나는 열여섯 건은 한 동 파일 맨 아래의 "합계" 줄과 빈 줄을 Codex가 데이터로 볼지 말지 오락가락한 데서 나왔습니다. 배 주무관이 합계 줄은 빼고 빈 줄만 버리라고 정리하자 건수가 맞았습니다. 한 동의 완료 건수는 원본을 직접 열어 세어 보았고, 그것도 맞았습니다.

마지막으로 `git status`를 쳤습니다. 원본 폴더에는 바뀐 파일이 하나도 없었습니다. 보고서 초안에서 "이관 건이 늘어난 것은 인력 부족 때문으로 보인다"는 문장에는 [짐작] 표시가 붙어 있었습니다. 배 주무관은 그 문장을 지우고 사실만 남겨 과장에게 올렸습니다. 그리고 AGENTS.md 맨 아래에 한 가지를 더 적었습니다. "합계 줄과 빈 줄은 데이터에서 뺀다." 다음 달에는 이 설명을 다시 하지 않아도 됩니다.

### 따라 하기
1. 업무 정리용 작업 폴더를 만들고 원본·작업·결과 하위 폴더를 나눈 뒤 `git init`을 합니다. 성공 기준: 폴더 이름에 한글과 공백이 없고, `git status`가 실행됩니다.
2. 합칠 파일 서너 개의 복사본을 원본 폴더에 넣습니다. 개인정보와 기밀 열은 넣기 전에 직접 지우고, 엑셀은 CSV(UTF-8)로 저장합니다. 그다음 커밋합니다. 성공 기준: 원본 폴더에 실명·연락처가 없고, `git log`에 첫 커밋이 보입니다.
3. AGENTS.md에 원본 보호 규칙을 적고 커밋합니다. 성공 기준: "원본 파일 하나를 고쳐 줘"라고 하면 규칙을 들어 거절하거나 먼저 묻습니다.
4. `codex --sandbox read-only --ask-for-approval on-request`로 켜고, 아래 첫 번째 프롬프트로 대응표와 이름 바꾸기 미리보기를 받습니다. 성공 기준: 파일이 하나도 바뀌지 않은 채 표만 돌아옵니다.
5. 대응표를 고친 뒤 `/permissions`로 Auto로 바꾸고 합치게 합니다. 성공 기준: 결과 폴더에 합친 파일이 생기고, `git status`에 원본 폴더의 변경이 없습니다.
6. 두 번째 프롬프트로 검산하고, 합계 하나는 원본을 직접 열어 비교합니다. 성공 기준: 건수가 원본 합과 같고, 내가 센 합계가 표와 맞습니다.
7. 세 번째 프롬프트로 보고서 초안을 받고, 확인이 끝나면 결과를 커밋합니다. 성공 기준: 숫자마다 출처나 계산식이 있고, 짐작인 문장이 따로 표시돼 있습니다.

### 복사해 쓰는 프롬프트
```text
원본 폴더의 파일들을 하나의 표로 합치려고 해. 지금은 읽기만 하고 아무 파일도 만들거나 고치지 마.
1. 파일마다 어떤 항목(열)이 있는지, 데이터가 몇 줄인지
2. 이름은 다르지만 같은 뜻으로 보이는 항목과 그렇게 본 이유
3. 날짜·상태 값 형식이 파일마다 어떻게 다른지, 통일한다면 어떤 형식으로 할지
4. 합계 줄, 빈 줄, 제목 줄처럼 데이터가 아닌 줄이 있는 파일
5. 파일 이름을 [이름 규칙]으로 바꾼다면 바꾸기 전과 후 이름 표. 어느 파일인지 모르겠으면 "확인 필요"로 표시해 줘
```

```text
결과 폴더의 합친 표를 검산해 줘. 고치지는 말고 보고만.
1. 원본 파일별 데이터 줄 수, 그 합계, 합친 표의 줄 수
2. 두 숫자가 다르면 어느 파일에서 몇 줄이 차이 나는지와 그 이유
3. 합친 표에서 비어 있는 값의 수와 그 값이 어느 원본에서 왔는지
4. git status 기준으로 원본 폴더에 바뀐 파일이 있는지
확인하지 못한 것은 확인하지 못했다고 적어 줘.
```

```text
합친 표를 바탕으로 [누구]에게 올릴 [보고서 종류] 초안을 결과 폴더에 새 파일로 만들어 줘.
- 숫자는 표에 있는 것만 쓰고, 계산한 값은 어떤 항목을 어떻게 계산했는지 옆에 적어 줘.
- 원인이나 해석처럼 표에서 바로 나오지 않는 문장은 [짐작]이라고 표시해 줘.
- 분량은 [한 페이지] 안으로.
```

|---|---|---|
| 엑셀을 읽으려다 설치 승인을 묻고 막힙니다 | 엑셀을 읽는 도구가 없고, 인터넷이 꺼져 있거나 회사 PC가 설치를 막습니다 | 엑셀에서 CSV(UTF-8)로 저장해 원본 폴더에 넣습니다 |
| 읽기 전용인데 파일을 만들려고 허락을 묻습니다 | 요청 문장이 실행 요청으로 읽혔습니다 | 거절하고, "아무 파일도 만들거나 고치지 마"를 첫 문장에 넣어 다시 요청합니다 |
| 합친 표의 건수가 원본 합과 다릅니다 | 합계 줄·빈 줄·제목 줄을 데이터로 읽거나 버렸습니다 | 차이 나는 파일을 직접 열어 보고, 뺄 줄과 남길 줄을 알려 준 뒤 AGENTS.md에도 적습니다 |
| `git status`에 원본 파일이 바뀌었다고 나옵니다 | 원본 폴더에서 이름을 바꾸거나 고쳤습니다 | 원본 폴더를 커밋 시점으로 되돌리고(26단계), 규칙을 다시 확인한 뒤 결과 폴더에 복사해 작업하게 합니다 |
| 한글이 깨져 보입니다 | 파일마다 인코딩이 다릅니다 | CSV로 저장할 때 UTF-8을 고르거나, 인코딩을 확인해 맞춰 달라고 합니다 |

### 스스로 점검
- [ ] 원본 폴더에 복사본만 넣고 커밋한 뒤, 작업이 끝나고 `git status`로 원본이 그대로인지 확인했습니까?
- [ ] 대응표를 받을 때는 읽기 전용으로, 합칠 때는 Auto로 권한을 바꿔 썼습니까?
- [ ] 합친 표의 건수와 합계 하나를 원본과 직접 맞춰 봤습니까?

### 기억할 것
- 파일이 많고 규칙이 되풀이되며 변경 기록이 필요한 일은 Codex로, 보고서 한 편은 Work로 맡기는 편이 편합니다.
- 원본은 복사본으로 가져와 커밋하고, 살필 때는 읽기 전용으로 켭니다. 원본이 그대로인지는 `git status`로 봅니다.
- 받은 결과는 건수·합계·빈 값·변경 내역으로 확인하고, 반복되는 설명은 AGENTS.md에 적어 둡니다.

## 35단계 · 여러 일을 동시에: 작업 트리와 클라우드

> 서로 부딪히지 않게 일을 나눠 맡기고, 결과는 PR로 받아 사람이 확인한 뒤 합칩니다.

**걸리는 시간** · 읽기 약 12분 · 따라 하기 약 60분

### 이 단계를 마치면
- Local, Worktree, Cloud 세 실행 위치의 차이를 설명하고 일에 맞게 고를 수 있습니다.
- 저장소 하나에 클라우드 환경을 만들고, 인터넷 접근을 필요한 만큼만 열 수 있습니다.
- 두세 가지 작업을 나란히 맡기고, 결과를 diff와 PR로 받아 직접 확인한 뒤 합칠 수 있습니다.

제3부에서는 폴더 하나를 열고 에이전트에게 한 가지씩 맡겼습니다. 작업이 끝날 때까지 화면을 지켜보다가, 끝나면 다음 일을 시켰습니다. 그런데 고칠 것이 세 가지라면 어떨까요? 안내 문구 수정, 내려받기 기능, 휴대폰 화면 정리를 한 폴더에서 동시에 시키면 서로의 변경이 뒤섞입니다. 하나씩 하자니 하루가 갑니다. 여러분이라면 어떻게 나누시겠습니까?

Codex에는 이 문제를 푸는 방법이 있습니다. 작업을 어디서 돌릴지 고르는 것입니다. 이 단계에서는 세 가지 실행 위치를 비교하고, 클라우드에서 여러 작업을 나란히 돌린 뒤 결과를 PR로 받는 순서를 익힙니다.

### 세 가지 실행 위치
ChatGPT 데스크톱 앱 안의 Codex는 작업을 시작할 때 실행 위치를 셋 가운데 하나로 고릅니다. 공식 문서의 이름을 그대로 쓰면 Local, Worktree, Cloud입니다.

| 실행 위치 | 어디서 도나 | 원래 폴더에 주는 영향 | 어울리는 일 |
|---|---|---|---|
| Local | 지금 연 폴더 | 파일이 바로 바뀝니다 | 한 가지 일을 지켜보며 할 때 |
| Worktree | Git 워크트리로 떼어 낸 별도 작업 공간 | 원래 폴더는 그대로 있고, 변경은 따로 모입니다 | 내 컴퓨터에서 두 가지 이상을 나란히 할 때 |
| Cloud | OpenAI의 클라우드 컨테이너 | 내 폴더는 건드리지 않고, 결과가 diff와 PR로 돌아옵니다 | 오래 걸리는 일, 여러 일을 한꺼번에 맡길 때 |

Local은 32~34단계에서 해 본 방식입니다. 지금 연 폴더에서 에이전트가 파일을 읽고 고칩니다. 가장 단순하지만 한 폴더에서 두 작업을 동시에 돌리면 서로의 변경이 섞입니다.

Worktree는 Git이 원래 가진 기능을 씁니다. 워크트리(worktree)는 같은 저장소를 폴더 여러 개로 펼쳐 두고, 폴더마다 다른 브랜치를 올려 두는 방법입니다. 26단계에서 브랜치를 "원본을 건드리지 않는 연습장"으로 설명했는데, 워크트리는 그 연습장을 아예 다른 책상에 펼쳐 두는 셈입니다. 한 작업이 파일을 고치는 동안 다른 작업은 다른 책상에서 일하니 서로 섞이지 않습니다. 다만 두 작업 모두 내 컴퓨터에서 돌고, Codex의 사용량도 그만큼 씁니다.

Cloud는 작업을 OpenAI의 클라우드 컨테이너로 보냅니다. 작업마다 따로 만든 환경에서 돌기 때문에 여러 작업을 동시에 맡길 수 있고, 같은 일을 여러 번 시도하게 해서 결과를 비교할 수도 있습니다. 결과는 요약과 diff로 돌아오고, 검토한 뒤 추가 지시를 하거나 PR을 엽니다.

데스크톱 앱과 IDE 확장에는 `/local`, `/worktree`, `/cloud`처럼 실행 위치와 같은 이름의 명령이 있습니다. 화면에서 고르는 위치는 버전마다 달라질 수 있으니, 버튼이 안 보이면 이 명령 이름으로 공식 문서를 찾아보십시오. 터미널을 쓴다면 `codex cloud`로 클라우드 작업 화면을 열고, `codex cloud exec`로 작업을 보내고, `codex cloud list`로 목록을 봅니다.

### 클라우드 환경과 인터넷 접근
클라우드를 쓰려면 먼저 몇 가지가 갖춰져야 합니다. 클라우드는 ChatGPT 계정으로 로그인했을 때만 쓸 수 있고, API 키 로그인으로는 쓸 수 없습니다. 요금표 기준으로 웹과 클라우드 연동은 Plus 요금제부터 들어 있습니다. 이메일과 비밀번호로 가입한 계정이라면 2단계 인증(MFA)을 먼저 켜야 합니다.

준비가 되면 순서는 이렇습니다. chatgpt.com/codex에 로그인하고 GitHub를 연결합니다. 환경 설정 화면(chatgpt.com/codex/settings/environments)에서 저장소마다 환경을 하나씩 만듭니다. 환경은 "이 저장소의 작업을 어떤 조건의 컴퓨터에서 돌릴지"를 적어 둔 설정입니다.

클라우드 작업이 도는 과정을 알아 두면 막혔을 때 원인을 찾기 쉽습니다.

1. 작업용 컨테이너를 만들고 저장소의 브랜치를 가져옵니다.
2. 설정 스크립트를 실행합니다. 필요한 프로그램을 설치하는 단계입니다.
3. 인터넷 접근 설정을 적용합니다.
4. 에이전트가 명령을 실행하며 일합니다.
5. 답변과 diff를 보여 줍니다.

기본 이미지는 `universal`이고, 만든 컨테이너는 최대 12시간 캐시되어 다음 작업이 더 빨리 시작됩니다. 환경 변수는 작업 내내 쓸 수 있지만, 시크릿(인증키처럼 숨겨야 하는 값)은 설정 스크립트 단계에서만 쓰이고 에이전트가 일하기 전에 지워집니다. 에이전트가 인증키를 들고 바깥 서비스를 부르는 시험은 클라우드에서 할 수 없다는 뜻입니다. 이 제약은 오히려 안전장치입니다.

인터넷은 에이전트 단계에서 기본으로 막혀 있습니다. 설정 스크립트 단계에서만 인터넷을 씁니다. 환경마다 Off와 On을 고를 수 있고, On으로 두면 허용할 도메인 목록(None, Common dependencies, All)과 허용할 HTTP 메서드를 정합니다. 메서드는 읽기에 해당하는 GET, HEAD, OPTIONS만 허용하도록 좁힐 수 있습니다. 공식 문서는 인터넷을 열면 웹 페이지에 숨은 지시에 에이전트가 휘둘리는 프롬프트 인젝션과, 코드나 자료가 바깥으로 새는 유출 위험이 생긴다고 경고합니다. 7단계의 원칙을 여기에도 적용합니다. 처음에는 Off로 두고, 설치할 것은 설정 스크립트로 옮깁니다. 그래도 인터넷이 필요하면 Common dependencies와 읽기 메서드만 허용하는 데서 시작합니다.

클라우드 작업도 AGENTS.md를 읽습니다. 공식 문서에 따르면 lint와 테스트 명령을 AGENTS.md에서 찾아 씁니다. 33단계에서 적은 "끝났다고 말하기 전에 할 확인"이 클라우드 작업에도 그대로 전해진다는 뜻입니다.

### 나란히 맡기고 PR로 받기
여러 작업을 동시에 맡길 때 가장 중요한 원칙은 하나입니다. 작업끼리 같은 파일을 건드리지 않게 나눕니다. 두 작업이 같은 파일의 같은 부분을 고치면, 나중에 합칠 때 충돌이 납니다. 충돌을 푸는 일은 비개발자에게 가장 어려운 일 가운데 하나입니다. 그래서 나누기 전에 에이전트에게 먼저 묻습니다. "이 세 가지 일이 각각 어떤 파일을 건드리는지, 겹치는 파일이 있는지 알려 줘."

작업 하나에 PR 하나를 원칙으로 합니다. PR이 작으면 읽기도 쉽고, 문제가 생겼을 때 그 PR만 되돌리면 됩니다. 같은 일을 여러 번 시도하게 하는 기능은 화면 시안처럼 정답이 하나로 정해지지 않는 일에 쓰면 좋습니다. 두 결과를 나란히 놓고 고른 쪽만 PR로 엽니다.

결과가 돌아오면 요약부터 읽고, 다음으로 diff를 봅니다. 요약에 "완료했습니다"라고 적혀 있어도 30단계의 표대로 나눠 읽습니다. 바뀐 파일 목록에 시키지 않은 파일이 있는지, 테스트를 실제로 돌렸는지 아니면 돌리지 못했는지를 확인합니다. 내 컴퓨터에서 직접 돌려 보고 싶으면 `codex apply`로 클라우드 결과를 로컬 폴더에 적용합니다. 적용하기 전에 새 브랜치로 옮기고 `git status`가 깨끗한지 확인해 두는 편이 안전합니다.

마지막으로 비용입니다. 로컬 작업과 클라우드 작업은 같은 사용량 한도를 나눠 씁니다. 작업을 동시에 여러 개 돌리면 한도도 그만큼 빨리 줄어듭니다. 남은 양은 사용량 대시보드(chatgpt.com/codex/settings/usage)나 CLI의 `/status`에서 확인합니다.

### 현장 장면
오세린 차장의 비품 신청 페이지에 고칠 것이 세 가지 쌓였습니다. 이번 달 신청 마감 안내 문구 바꾸기, 신청 목록을 CSV로 내려받는 버튼, 휴대폰에서 글자가 너무 작다는 불만. 예전 같으면 사흘에 나눠 했을 일입니다.

오 차장은 먼저 로컬에서 Codex에게 물었습니다. "이 세 가지가 각각 어떤 파일을 건드리는지 알려 줘. 고치지는 마." 답을 보니 문구 수정과 글자 크기가 같은 화면 파일을 건드렸습니다. 오 차장은 두 일을 하나로 묶고, 내려받기 버튼을 따로 떼어 작업 두 개로 나눴습니다.

클라우드 환경은 인터넷을 Off로 두고 만들었습니다. 두 작업을 보내고 회의에 들어갔다 나오니 결과가 와 있었습니다. 화면 작업은 깔끔했습니다. 그런데 내려받기 작업의 요약 끝에 이런 문장이 있었습니다. "필요한 패키지를 설치하지 못해 테스트를 실행하지 못했습니다." 인터넷이 막혀 있으니 에이전트 단계에서 설치가 안 된 것입니다. 오 차장은 인터넷을 켜는 대신, 설치 명령을 설정 스크립트로 옮기는 방법을 Codex에게 물었습니다. 설정 스크립트를 고친 뒤 같은 작업을 다시 보내자 이번에는 테스트까지 돌았다는 보고가 왔습니다.

오 차장은 두 결과를 각각 PR로 열었습니다. 화면 PR을 먼저 합치고 배포된 주소를 휴대폰으로 열어 글자 크기를 확인했습니다. 내려받기 PR은 CSV 파일을 엑셀로 열어 한글이 깨지지 않는지, 건수가 화면의 신청 건수와 같은지, 신청자가 부서명으로만 나오는지 맞춰 본 뒤 합쳤습니다. 그날 오후 오 차장은 AGENTS.md에 한 문장을 보탰습니다. "클라우드 작업에서 테스트를 돌리지 못했으면 요약 첫머리에 적는다."

### 따라 하기
1. 내 도구의 로컬 폴더에서 `git status`로 변경 사항이 없는지 확인하고, 최신 커밋을 GitHub에 푸시합니다. 성공 기준: GitHub 화면의 최근 커밋과 내 폴더의 최근 커밋이 같습니다.
2. chatgpt.com/codex에 ChatGPT 계정으로 로그인하고 GitHub를 연결한 뒤, 환경 설정 화면에서 내 도구 저장소의 환경을 만듭니다. 인터넷 접근은 Off로 둡니다. 성공 기준: 환경 목록에 내 저장소가 보입니다.
3. 첫 클라우드 작업으로 "이 저장소의 구조와 테스트 명령을 설명해 줘. 파일은 고치지 마."를 보냅니다. 성공 기준: 설명이 돌아오고 diff가 비어 있습니다. 설치 실패가 보이면 아래 두 번째 프롬프트로 설정 스크립트를 고칩니다.
4. 고칠 것 두세 가지를 적고, 아래 첫 번째 프롬프트로 겹치는 파일이 없게 나눕니다. 성공 기준: 작업마다 건드릴 파일 목록이 있고, 서로 겹치지 않습니다.
5. 나눈 작업을 클라우드로 나란히 보냅니다. 세 번째 프롬프트를 작업마다 붙입니다. 성공 기준: 작업마다 요약과 diff가 돌아오고, 테스트를 돌렸는지가 적혀 있습니다.
6. 결과 하나를 골라 PR로 열고, 바뀐 파일과 확인한 방법을 PR 설명에 적은 뒤 합칩니다. 합친 뒤에는 배포된 주소에서 확인합니다. 성공 기준: 휴대폰으로 연 주소에서 바뀐 내용이 보이고, 나머지 작업도 같은 순서로 처리했습니다.

## 36단계 · GitHub 코드 리뷰를 Codex에게

> PR마다 다른 에이전트가 한 번 더 읽게 하고, 지적을 받아들일지는 사람이 정합니다.

**걸리는 시간** · 읽기 약 12분 · 따라 하기 약 40분

### 이 단계를 마치면
- 내 저장소에 Codex 코드 리뷰를 켜고, `@codex review`로 리뷰를 부를 수 있습니다.
- AGENTS.md의 `## Code Review Rules`에 우리 도구에 맞는 리뷰 기준을 적을 수 있습니다.
- 리뷰 지적마다 받아들일지, 보류할지, 반박할지를 정하고 그 이유를 PR에 남길 수 있습니다.

제3부에서 우리는 에이전트가 만든 것을 스스로 확인했습니다. 화면을 열고, 바뀐 파일을 묻고, 테스트를 되돌려 봤습니다. 그런데 회사에서 누군가 이렇게 묻는다면 어떨까요? "이 변경을 만든 사람 말고 누가 봤습니까?" 개발팀에서는 이 질문에 답하려고 코드 리뷰를 합니다. 변경을 바로 본줄에 넣지 않고 PR로 올린 뒤, 다른 사람이 읽고 승인하면 합칩니다.

비개발자 혼자 만드는 도구에는 읽어 줄 동료가 없습니다. Codex의 GitHub 연동이 그 빈틈을 일부 메워 줍니다. PR에 댓글 하나를 달면 Codex가 변경 내용을 읽고 리뷰를 올립니다. 이 단계에서는 리뷰를 켜는 법, 부르는 법, 그리고 가장 중요한 일인 지적을 판단하는 법을 익힙니다.

### 켜는 법과 부르는 법
Codex 코드 리뷰는 Codex cloud 위에서 돌아갑니다. 그래서 35단계의 클라우드 설정이 먼저 되어 있어야 합니다. 로그인은 ChatGPT 계정이어야 하고, API 키 로그인으로는 쓸 수 없습니다. 요금표 기준으로 자동 코드 리뷰 같은 클라우드 연동은 Plus 요금제부터 들어 있습니다.

켜는 곳은 Codex 설정의 코드 리뷰 화면(chatgpt.com/codex/settings/code-review)입니다. 저장소 목록에서 내 저장소의 Code review를 켭니다. 이 설정을 바꾸려면 그 저장소에 push 권한이나 admin 권한이 있어야 합니다. 25단계에서 만든 개인 저장소라면 주인이니 문제가 없고, 회사 저장소라면 관리자에게 부탁해야 합니다.

부르는 방법은 두 가지입니다.

| 방법 | 하는 법 | 언제 쓰나 |
|---|---|---|
| 수동 리뷰 | PR 댓글에 `@codex review`를 적습니다 | 중요한 변경만 골라 보고 싶을 때 |
| 초점 리뷰 | `@codex review for issues in the database migration`처럼 뒤에 볼 곳을 붙입니다 | 특정 위험만 따로 확인하고 싶을 때 |
| 자동 리뷰 | 같은 설정 화면에서 Automatic reviews를 켭니다 | 모든 PR을 빠짐없이 보게 하고 싶을 때 |

`@codex review`를 달면 Codex가 👀 반응을 답니다. 읽기 시작했다는 표시입니다. 잠시 뒤 리뷰가 올라옵니다. 공식 문서에 따르면 GitHub에는 P0과 P1 등급의 문제만 표시합니다. P0, P1은 개발 현장에서 흔히 쓰는 우선순위 표시로, 숫자가 작을수록 급한 문제입니다. 사소한 취향 지적으로 PR이 뒤덮이지 않도록 걸러 낸 셈입니다.

`@codex` 뒤에 review가 아닌 다른 말을 붙이면 리뷰 대신 작업이 시작됩니다. 예를 들어 `@codex fix the P1 issue`라고 쓰면 그 PR을 맥락으로 클라우드 작업이 돌아 고친 결과를 내놓습니다. 편하지만, 지적을 판단하기 전에 바로 고치게 하면 판단을 건너뛰게 됩니다. 아래 순서대로 먼저 판단하고, 고칠 것만 맡기십시오. 보안 쪽만 따로 보는 `@codex security review`도 있는데, 집필 시점에는 연구 프리뷰 단계입니다.

PR을 올리기 전에 내 컴퓨터에서 먼저 리뷰를 받을 수도 있습니다. Codex CLI에서 `/review`를 입력하거나, 터미널에서 `codex review --uncommitted`(아직 커밋하지 않은 변경), `codex review --base main`(본줄과 다른 부분)을 실행합니다. 로컬 리뷰로 한 번 거르고, PR에서 한 번 더 받는 순서가 좋습니다.

### 리뷰 규칙은 AGENTS.md에
리뷰가 무엇을 볼지는 AGENTS.md의 `## Code Review Rules` 섹션에 적습니다. 33단계에서 만든 AGENTS.md 아래에 섹션을 하나 더 붙이면 됩니다. 규칙은 23단계에서 배운 대로 확인할 수 있는 문장으로 씁니다.

```markdown
## Code Review Rules
- 개인정보(이름 전체, 전화번호, 이메일)가 화면, 주소창, 내려받는 파일에 그대로 나오면 P1로 표시한다.
- 인증키나 비밀번호로 보이는 문자열이 코드에 있으면 P0으로 표시한다.
- 화면 문구는 한국어여야 한다. 영어 오류 문구가 사용자에게 보이면 표시한다.
- 이 도구에는 관리자 로그인이 없다. 관리자 권한 검사가 없다는 지적은 하지 않는다.
- 리뷰 설명은 한국어로 쓴다.
```

마지막 규칙처럼 언어를 정해 둘 수 있지만, 실제로 따르는지는 첫 리뷰에서 확인해야 합니다. 규칙 파일은 부탁이라는 29단계의 말이 여기에도 해당합니다.

### 지적을 사람이 판단하는 법
리뷰가 올라오면 고치기 전에 지적마다 판단부터 합니다. 리뷰어는 코드를 읽었을 뿐, 우리 도구를 누가 어떻게 쓰는지는 모릅니다. 그 맥락을 아는 사람은 만든 사람입니다.

| 판단 | 이럴 때 | PR에 남길 것 |
|---|---|---|
| 받아들임 | 지적한 문제를 화면에서 재현할 수 있습니다 | 재현한 방법, 고친 커밋 |
| 보류 | 맞는 말이지만 지금 고치면 범위가 커집니다 | 나중에 할 일 목록에 올렸다는 기록 |
| 반박 | 우리 도구의 쓰임과 맞지 않습니다 | 이유 한두 문장, 필요하면 Code Review Rules에 추가 |
| 모름 | 무슨 뜻인지 이해하지 못했습니다 | 다른 에이전트나 사람에게 물어본 결과 |

비개발자가 리뷰를 읽을 때는 세 가지만 확인하면 됩니다. 첫째, 어떤 파일의 어느 부분을 가리키는가. 둘째, 그 문제가 사용자에게 어떤 모습으로 나타나는가. 셋째, 내가 화면에서 직접 재현할 수 있는가. 셋째가 가장 중요합니다. 재현이 안 되는 지적은 곧바로 고치지 말고, Codex나 Claude Code에게 "이 지적을 내가 화면에서 확인하는 방법을 알려 줘. 고치지는 마"라고 먼저 묻습니다.

리뷰가 아무 지적도 하지 않았다고 해서 문제가 없다는 뜻은 아닙니다. P0, P1만 표시하니 작은 문제는 걸러졌을 수 있고, 리뷰어가 못 본 문제도 있습니다. 리뷰는 30단계의 확인을 대신하지 않습니다. 확인 위에 한 겹을 더하는 일입니다.

### 현장 장면
가람시 민원여권과 배수민 주무관은 34단계에서 민원 현황 파일을 Codex로 합친 뒤, 제3부의 방법으로 만들어 둔 민원 서류 안내 페이지에도 Codex를 붙이기로 했습니다. 어떤 민원에 어떤 서류가 필요한지 고르면 목록이 나오고, 문의 양식에 이름과 연락처를 남기면 담당자가 전화를 거는 페이지입니다. 시 정보통신팀은 외부에 공개하기 전에 한 가지를 요구했습니다. "변경마다 검토 흔적을 남겨 주세요."

배 주무관은 자동 리뷰를 켜고, 문의 양식을 손본 PR을 올렸습니다. 몇 분 뒤 리뷰 두 건이 달렸습니다. 첫째는 P1이었습니다. 문의 양식을 보내면 입력한 이름과 전화번호가 주소창에 그대로 붙는다는 지적이었습니다. 배 주무관은 휴대폰으로 배포된 주소를 열어 가짜 이름을 넣고 보내 봤습니다. 주소창 끝에 이름과 번호가 보였습니다. 이 주소가 방문 기록에 남으면 개인정보가 새는 셈입니다. 받아들이고, 재현한 방법을 PR 댓글에 적은 뒤 고치게 했습니다.

둘째 지적은 관리자 화면에 비밀번호 확인이 없다는 내용이었습니다. 그런데 이 페이지에는 관리자 화면이 없었습니다. 문의 내용은 담당자 메일로 가고, 페이지에는 저장되지 않습니다. 배 주무관은 이유를 두 문장으로 적어 반박하고, AGENTS.md의 Code Review Rules에 "이 도구에는 관리자 화면이 없다"는 규칙을 보탰습니다. 다음 PR부터 같은 지적은 나오지 않았습니다.

정보통신팀 담당자는 PR 목록을 훑어보고 말했습니다. "지적마다 판단한 이유가 있으니 검토 기록으로 충분하네요." 배 주무관이 PR에 남긴 판단의 기록이 곧 검토 흔적이 된 셈입니다.

### 따라 하기
1. 35단계의 클라우드 환경이 내 저장소에 있는지 확인합니다. 성공 기준: chatgpt.com/codex의 환경 목록에 저장소가 보입니다.
2. 코드 리뷰 설정 화면에서 내 저장소의 Code review를 켭니다. 자동 리뷰는 아직 켜지 않습니다. 성공 기준: 저장소 옆의 리뷰 설정이 켜져 있습니다.
3. AGENTS.md에 `## Code Review Rules` 섹션을 붙이고 규칙 세 개 이상을 적어 커밋합니다. 아래 첫 번째 프롬프트로 초안을 받아도 됩니다. 성공 기준: 규칙마다 화면이나 파일에서 지켜졌는지 가릴 수 있습니다.
4. 작은 변경 하나를 브랜치에서 만들어 PR을 열고, 댓글에 `@codex review`를 적습니다. 성공 기준: 👀 반응이 붙고 리뷰가 올라옵니다.
5. 지적마다 받아들임·보류·반박·모름 가운데 하나를 고르고, 이유를 PR 댓글로 남깁니다. 두 번째 프롬프트로 재현 방법을 물을 수 있습니다. 성공 기준: 지적 하나도 빠짐없이 판단이 적혀 있습니다.
6. 받아들인 것만 고치게 하고, 고친 뒤 다시 `@codex review`를 부릅니다. 괜찮으면 합치고, 자동 리뷰를 켤지 정합니다. 성공 기준: 합친 뒤 배포된 주소에서 고친 부분을 직접 확인했습니다.

### 복사해 쓰는 프롬프트

```text
- 우리 도구에 없는 기능(예: [없는 기능])에 대한 지적은 하지 말라는 규칙
- 규칙마다 P0인지 P1인지 표시
- 규칙은 사람이 지켜졌는지 예·아니오로 가릴 수 있는 문장으로
```

## 37단계 · 설정·스킬·MCP로 넓히기

> 자주 바꾸는 선택은 설정 파일에, 되풀이하는 일은 스킬에, 바깥 도구는 MCP에 맡기고, 자동으로 돌리는 일은 읽기 전용에서 시작합니다.

**걸리는 시간** · 읽기 약 15분 · 따라 하기 약 60분

### 이 단계를 마치면
- `~/.codex/config.toml`의 주요 설정을 읽고, 내게 맞게 몇 가지를 바꿀 수 있습니다.
- 스킬, 플러그인, MCP, 훅, 서브에이전트가 Codex에서 어디에 있고 어떻게 확인하는지 압니다.
- Claude Code 설정을 `/import`로 가져오고, `codex exec`로 읽기 전용 점검 하나를 돌릴 수 있습니다.

Codex를 며칠 써 보면 같은 선택을 매번 반복하고 있다는 것을 알게 됩니다. 켤 때마다 모델을 고르고, 권한을 바꾸고, 같은 설명을 다시 붙여 넣습니다. 29단계에서 Claude Code를 넓혔던 것처럼, Codex에도 이런 반복을 줄이는 장치가 있습니다. 이름도 대부분 같습니다. 이 단계에서는 그 장치들이 Codex에서는 어디에 있는지 살펴보고, 마지막에 대화 없이 한 번 돌고 끝나는 `codex exec`를 자동 점검에 붙여 봅니다.

### config.toml: 매번 고르던 것을 적어 두는 곳
Codex의 설정은 `config.toml`이라는 파일에 모입니다. 내 계정 전체에 쓰는 설정은 `~/.codex/config.toml`에, 특정 프로젝트에만 쓰는 설정은 그 폴더의 `.codex/config.toml`에 둡니다. 프로젝트 설정은 내가 신뢰한다고 표시한 프로젝트에서만 읽습니다. CLI, IDE 확장, 데스크톱 앱이 같은 설정을 함께 씁니다.

설정이 여러 곳에 있으면 순서대로 우선합니다. 실행할 때 붙인 옵션과 `-c`가 가장 먼저이고, 다음이 프로젝트 설정, 프로필, 사용자 설정, 클라우드 관리 설정, 시스템 설정, 기본값 순입니다. 프로필은 `~/.codex/<이름>.config.toml`에 두고 `--profile`로 골라 씁니다. 예를 들어 "읽기만 하는 점검용" 프로필을 따로 두면 편합니다.

자주 보는 설정은 아래와 같습니다. 모델 이름은 집필 시점 기준입니다.

```toml
model = "gpt-6-sol"                 # 기본 모델
model_reasoning_effort = "medium"   # 추론 강도
approval_policy = "on-request"      # 언제 멈추고 묻는가
sandbox_mode = "workspace-write"    # 무엇을 할 수 있는가
web_search = "cached"               # 미리 색인한 검색 결과만 쓴다

[sandbox_workspace_write]
network_access = false              # 작업 중 인터넷은 끈다
```

`approval_policy`와 `sandbox_mode`는 33단계에서 다룬 두 층입니다. 추론 강도는 모델이 지원하는 값 가운데서 고르고, 화면에는 Light(CLI에서는 Low), Medium, High, Extra High, Max, Ultra로 나옵니다. 강도를 높이면 더 오래 생각하는 대신 사용량을 더 씁니다. 웹 검색은 기본이 `cached`이고, 실시간 검색이 필요하면 `"live"`로 바꾸거나 실행할 때 `--search`를 붙입니다.

회사에서 여러 사람이 Codex를 쓴다면, 관리자가 `requirements.toml`로 승인 정책과 샌드박스를 강제할 수 있다는 것도 알아 두십시오. 예를 들어 전부 허용하는 설정을 아예 못 쓰게 막을 수 있습니다. 개인이 설정을 바꿨는데 적용되지 않는다면 이런 관리 설정 때문일 수 있습니다.

### 자주 쓰는 / 명령
Codex CLI 안에서 `/`를 치면 명령 목록이 나옵니다. 처음에는 아래 정도만 알면 충분합니다.

| 명령 | 하는 일 | 이럴 때 |
|---|---|---|
| `/status` | 모델, 승인 정책, 쓰기 가능 폴더, 남은 맥락, 사용량 표시 | 지금 어떤 조건으로 돌고 있는지 모를 때 |
| `/permissions` | 승인과 샌드박스 범위 바꾸기 | 읽기 전용과 Auto 사이를 오갈 때 |
| `/plan` | 계획 모드로 전환(Shift+Tab으로도 됨) | 여러 파일에 걸친 일을 맡기기 전 |
| `/diff`, `/review` | 바뀐 내용 보기, 작업 트리 리뷰 | 커밋하기 전 |
| `/compact`, `/new` | 대화를 요약해 맥락 확보, 새 대화 시작 | 대화가 길어졌거나 주제가 바뀌었을 때 |
| `/skills`, `/plugins`, `/mcp`, `/hooks` | 스킬, 플러그인, MCP 도구, 훅 확인 | 무엇이 켜져 있는지 볼 때 |
| `/import` | Claude Code 설정 가져오기 | Codex를 처음 들일 때 |

한 가지 주의할 점이 있습니다. 집필 시점의 CLI 명령 목록에는 되돌리기 명령 `/undo`가 없습니다. 되돌리기는 26단계에서 익힌 Git 커밋으로 합니다. 작업 전후로 커밋해 두는 습관이 Codex에서는 더 중요합니다. 데스크톱 앱의 리뷰 화면에서는 파일이나 변경 덩어리 단위로 되돌릴 수 있습니다.

### 스킬, 플러그인, MCP, 훅, 서브에이전트
Claude Code에서 익힌 장치들이 Codex에도 있습니다. 이름과 위치만 정리해 둡니다.

**스킬.** 특정 일을 하는 방법과 양식, 참고 자료를 묶은 꾸러미입니다. Codex에서는 `$스킬이름`으로 부르고, `/skills`로 목록을 봅니다. 새 스킬은 `$skill-creator`에게 만들어 달라고 하면 됩니다. 스킬은 ChatGPT와 Codex가 함께 쓰는데, ChatGPT에서는 `@`로 부릅니다.

**플러그인.** 스킬, MCP 서버, 훅 같은 것을 한 묶음으로 설치하는 단위입니다. CLI에서는 `/plugins`로 둘러봅니다. 웹, 데스크톱, 모바일, CLI에서 쓸 수 있지만 IDE 확장에서는 쓸 수 없습니다.

**MCP.** 64단계에서 자세히 다룰 연결 표준입니다. Codex에서는 터미널에서 `codex mcp add <이름> -- <실행 명령>`으로 붙이고, `codex mcp list`로 목록을 보고, 로그인이 필요한 서버는 `codex mcp login <이름>`으로 인증합니다. 설정 파일에서는 `[mcp_servers.<이름>]` 아래에 적고, 대화 중에는 `/mcp`로 확인합니다. 데스크톱 앱과 IDE에서는 설정 > MCP servers > Add server로 추가합니다. 셋 모두 같은 MCP 설정을 씁니다. 29단계의 원칙은 그대로입니다. 읽기만 하는 연결부터 시작하고, 누가 만든 서버인지, 회사가 허락한 것인지 먼저 확인합니다.

**훅.** 정해진 순간에 반드시 실행되는 명령입니다. Codex에서는 `hooks.json`이나 config.toml의 `[hooks]`에 적고, `/hooks`에서 보고, 승인하고, 끕니다. 도구를 쓰기 전과 후, 작업을 마칠 때, 세션을 시작할 때 같은 순간에 걸 수 있습니다.

**서브에이전트.** 일을 나눠 맡는 보조 에이전트입니다. 직접 정의한 에이전트는 `~/.codex/agents/`나 프로젝트의 `.codex/agents/` 폴더에 두고, `/agent`로 스레드를 오갑니다.

### Claude Code 설정 가져오기와 `codex exec`
제3부에서 Claude Code에 쌓아 둔 설정을 처음부터 다시 만들 필요는 없습니다. Codex CLI에서 `/import`를 입력하면 Claude Code의 설정, 스킬, 플러그인, 프로젝트, 최근 대화를 가져옵니다. 데스크톱 앱은 Claude Cowork에서도 가져올 수 있습니다. 가져와도 Claude Code 쪽 설정은 바뀌지 않습니다. 다만 무엇이 넘어왔는지는 직접 확인하십시오. 가져온 뒤 `/skills`, `/mcp`, `/hooks`를 차례로 열어 보면 됩니다.

`codex exec`(줄여서 `codex e`)는 대화 없이 한 번 실행하고 끝나는 명령입니다. 74~76단계에서 다룰 자동화에 Codex를 붙일 때 쓰는 입구입니다. 가장 중요한 특징은 **기본값이 읽기 전용 샌드박스**라는 점입니다. 따로 허락하지 않으면 파일을 읽고 보고만 하고, 고치지는 못합니다. 고치게 하려면 `--sandbox workspace-write`를 붙여야 합니다. 자동으로 도는 일일수록 사람이 지켜보지 않으니, 읽기 전용에서 시작하는 편이 안전합니다.

```bash
codex exec -o 점검결과.md "AGENTS.md의 확인 절차대로 이 저장소를 점검하고, 문제만 목록으로 보고해 줘. 파일은 고치지 마."
```

`-o`는 최종 답을 파일로 남기는 옵션입니다. 이 밖에 진행 상황을 기계가 읽기 좋은 형식으로 내보내는 `--json`, 기록을 남기지 않는 `--ephemeral`, 지난 실행을 이어 가는 `codex exec resume --last`가 있습니다. 예전 안내에 나오는 `--full-auto`는 사용 중단 예정입니다.

GitHub Actions처럼 서버에서 돌리는 자동화에는 API 키 로그인을 권장합니다. 이때 키는 한 번 실행할 때만 넘기고, 저장소 코드를 실행하는 작업 전체에 키를 환경 변수로 깔아 두지 말라고 공식 문서가 경고합니다. GitHub용으로는 `openai/codex-action@v1`이라는 Action이 따로 있습니다. 정해진 시간마다 돌리는 예약 작업은 CLI에서는 만들 수 없고, ChatGPT 웹이나 데스크톱 앱의 Scheduled 화면에서 만듭니다.

### 현장 장면
33단계에서 오세린 차장은 CLAUDE.md의 규칙만 손으로 AGENTS.md에 옮겼습니다. 이번에는 나머지를 옮길 차례였습니다. `/import`를 실행하자 Claude Code에서 쓰던 설정과 "푸시 전 점검" 스킬을 가져왔다는 안내가 나왔습니다. 오 차장은 안내만 믿지 않고 `/skills`와 `/hooks`를 차례로 열었습니다. 스킬은 목록에 있었습니다. 29단계에서 만든 인증키 검사 훅은 가져오기 안내만으로는 켜졌는지 알 수 없어, `/hooks`에서 무엇을 검사하는지 읽어 보고 직접 확인했습니다. 오 차장은 메모에 적었습니다. "가져온 뒤에는 목록을 연다."

다음은 매주 금요일마다 하던 점검이었습니다. 비품 신청 페이지의 안내 문구에 지난 분기 날짜가 남아 있는지, 신청자가 부서명이 아닌 이름으로 나오는 곳이 없는지를 눈으로 훑는 일이었습니다. 오 차장은 이 점검을 `codex exec` 명령 하나로 만들고, 결과를 `점검결과.md`로 받게 했습니다. 첫 실행 결과에는 "2분기 신청 마감"이라는 문구가 두 곳 남아 있다는 보고가 있었습니다. 오 차장은 파일이 하나도 바뀌지 않았다는 것을 `git status`로 확인했습니다. 읽기 전용 기본값이 제대로 지켜진 것입니다. 문구는 평소처럼 Local에서 고치고 커밋했습니다.

욕심도 났습니다. 분기별 비품 예산표가 있는 문서 창고를 MCP로 연결하면 예산 잔액을 화면에 자동으로 띄울 수 있을 것 같았습니다. 하지만 그 문서 창고에 쓰기 권한까지 주는 연결인지 알 수 없었습니다. 오 차장은 그 생각을 "IT팀에 물어볼 것" 목록에 올려 두었습니다.

### 따라 하기
1. Codex CLI에서 `/status`를 입력해 지금 모델, 승인 정책, 쓰기 가능 폴더를 확인합니다. 성공 기준: 세 가지를 메모에 옮겨 적었습니다.
2. `~/.codex/config.toml`을 열어(없으면 아래 첫 번째 프롬프트로 초안을 받아) 모델, 추론 강도, 승인 정책, 샌드박스가 무엇으로 되어 있는지 읽습니다. 바꿀 것이 있으면 하나만 바꿉니다. 성공 기준: Codex를 다시 켠 뒤 `/status`에 바꾼 값이 보입니다.
3. `/import`로 Claude Code 설정을 가져온 뒤, `/skills`, `/mcp`, `/hooks`를 차례로 엽니다. 성공 기준: 넘어온 것과 넘어오지 않은 것을 목록으로 적었습니다.
4. 되풀이하는 점검 하나를 정해 아래 두 번째 프롬프트를 `codex exec -o 점검결과.md "..."` 형태로 실행합니다. 성공 기준: `점검결과.md`에 보고가 남고, `git status`에 바뀐 파일이 없습니다.
5. 붙이고 싶은 MCP 서버가 있다면 이름, 만든 곳, 읽기·쓰기 여부를 적고, 허락을 받기 전에는 연결하지 않습니다. 성공 기준: "다음에 붙일 것" 목록에 올라가 있습니다.

## 38단계 · Claude Code와 Codex 나란히 쓰기

> 한쪽이 만들고 다른 쪽이 검토하게 하면, 한 에이전트로는 보이지 않던 실수가 드러납니다.

**걸리는 시간** · 읽기 약 12분 · 따라 하기 약 50분

### 이 단계를 마치면
- 우리 팀 기준으로 어떤 일을 Claude Code에, 어떤 일을 Codex에 맡길지 표로 정할 수 있습니다.
- 한쪽이 만든 PR을 다른 쪽이 검토하는 교차 검토를 한 번 끝까지 해 볼 수 있습니다.
- CLAUDE.md와 AGENTS.md가 서로 어긋나지 않게 함께 관리할 수 있습니다.

이제 여러분의 저장소에는 에이전트가 둘 있습니다. 제3부에서 함께 일한 Claude Code와, 이번 부에서 들인 Codex입니다. 둘 다 파일을 읽고 고치고 명령을 실행하며, 둘 다 규칙 파일을 읽고 계획을 먼저 내놓습니다. 그렇다면 무엇을 누구에게 맡겨야 할까요? 그리고 둘이 같은 저장소에서 일할 때 무엇을 조심해야 할까요?

이 단계의 답은 간단합니다. 일을 나누는 기준은 우리 팀이 정하고, 두 에이전트는 서로를 검토하는 데 씁니다. 사람이 판단하고 합친다는 원칙은 그대로입니다.

### 어떤 일을 어디에 맡길까
어느 에이전트가 더 뛰어난지는 이 책에서 판정하지 않습니다. 모델은 몇 주마다 바뀌고, 같은 일도 저장소와 요청 방식에 따라 결과가 달라집니다. 대신 기능과 환경의 차이로 나눕니다. 아래 표는 출발점일 뿐이니, 한 달쯤 써 본 뒤 우리 팀 경험으로 고쳐 쓰십시오.

| 일 | 먼저 맡길 곳 | 이유 |
|---|---|---|
| 이미 CLAUDE.md와 훅이 갖춰진 도구의 기능 추가 | Claude Code | 제3부에서 쌓은 규칙과 장치를 그대로 씁니다 |
| 서로 겹치지 않는 작은 수정 여러 개 | Codex 클라우드 | 여러 작업을 나란히 돌리고 PR로 받습니다(35단계) |
| 모든 PR에 대한 자동 리뷰 | Codex GitHub 리뷰 | `@codex review`와 자동 리뷰가 GitHub에 붙어 있습니다(36단계) |
| 한쪽이 만든 변경의 검토 | 만들지 않은 쪽 | 같은 가정 안에서 보지 않게 합니다 |
| 대화 없이 도는 정기 점검 | 두 도구 모두 가능, Codex는 `codex exec` | Codex는 기본이 읽기 전용이라 시작하기 쉽습니다(37단계) |
| 회사가 이미 쓰는 요금제로 해결되는 일 | 그 요금제의 도구 | 새 계약과 보안 검토를 줄입니다 |

표에서 가장 중요한 것은 넷째 항목입니다. 두 에이전트를 들인 가장 큰 이유가 교차 검토이기 때문입니다.

### 교차 검토: 만든 쪽과 보는 쪽을 나눈다
교차 검토는 한쪽 에이전트가 만든 변경을 다른 쪽 에이전트가 검토하게 하는 방법입니다. 29단계에서 검토만 맡는 서브에이전트를 두었던 것과 같은 원리인데, 이번에는 아예 다른 회사가 만든 모델이 봅니다. 훈련과 습관이 다르니 놓치는 곳도 다를 가능성이 큽니다.

가장 쉬운 조합은 이렇습니다. Claude Code로 기능을 만들어 PR을 올리고, 그 PR에 `@codex review`를 부릅니다. 반대 방향도 됩니다. Codex 클라우드가 만든 PR을 로컬로 받아, Claude Code에게 "이 브랜치에서 바뀐 내용을 읽고 보고만 해 줘"라고 맡깁니다.

교차 검토에는 규칙 세 가지가 필요합니다.

첫째, 검토하는 쪽에는 고치는 권한을 주지 않습니다. 검토자가 바로 고치기 시작하면 누가 무엇을 바꿨는지 흐려집니다. Codex라면 읽기 전용 샌드박스로, Claude Code라면 "고치지 말고 보고만"으로 요청합니다.

둘째, 두 쪽에 같은 기준을 줍니다. 만든 쪽이 따른 규칙과 검토하는 쪽이 보는 기준이 다르면, 검토는 취향 싸움이 됩니다. 아래에서 다룰 공통 규칙이 이 기준이 됩니다.

셋째, 의견이 갈리면 사람이 화면에서 확인합니다. Codex는 문제라고 하고 Claude Code는 괜찮다고 할 때, 어느 쪽 말을 믿을지 정하는 방법은 하나뿐입니다. 36단계처럼 재현해 봅니다. 재현되면 받아들이고, 안 되면 이유를 적어 둡니다. 두 에이전트에게 서로의 의견을 전달해 토론시키는 방법도 있지만, 결론은 사람이 냅니다.

### 규칙 파일 두 개를 함께 관리하기
두 에이전트가 한 저장소에서 일하면 규칙 파일도 둘이 됩니다. Claude Code는 CLAUDE.md를, Codex는 AGENTS.md를 읽습니다. 공식 문서 기준으로 Codex는 CLAUDE.md를 자동으로 읽지 않습니다. 기본으로 읽는 파일은 AGENTS.override.md와 AGENTS.md뿐입니다.

관리하는 방법은 세 가지입니다.

| 방법 | 하는 법 | 주의할 점 |
|---|---|---|
| 공통 규칙을 두 파일에 똑같이 둔다 | 두 파일 맨 위에 "공통 규칙" 섹션을 같은 문장으로 두고, 도구별 내용은 그 아래에 적습니다 | 한쪽만 고치면 어긋납니다. 고칠 때는 두 파일을 한 커밋에 함께 고칩니다 |
| Codex가 CLAUDE.md도 읽게 한다 | config.toml의 `project_doc_fallback_filenames`에 `CLAUDE.md`를 넣습니다 | Codex는 폴더마다 한 파일만 읽습니다. 같은 폴더에 AGENTS.md가 있으면 그쪽을 읽습니다. 실제로 읽히는지 직접 시험해야 합니다 |
| 한 번 가져오고 따로 관리한다 | `/import`로 Claude Code 설정을 가져온 뒤 AGENTS.md를 다듬습니다 | 가져온 뒤부터는 두 파일이 따로 변합니다. 정기적으로 비교합니다 |

둘째 방법은 공식 문서에 설정 방법이 나와 있지만, 이 책을 쓰면서 CLAUDE.md를 넣어 직접 시험하지는 못했습니다. 쓰려면 규칙 하나를 일부러 CLAUDE.md에만 적고 Codex가 그 규칙을 아는지 물어 확인하십시오.

어느 방법을 고르든 한 달에 한 번은 두 파일을 비교합니다. 아래 두 번째 프롬프트를 쓰면 됩니다. 규칙 파일이 어긋나면 두 에이전트가 서로의 작업을 되돌리는 일이 생깁니다. 현장 장면이 바로 그 이야기입니다.

### 비용과 요금제
두 도구를 쓰면 구독도 둘입니다. 결정하기 전에 확인할 것을 정리해 둡니다. 가격은 집필 시점 기준이고 자주 바뀝니다.

Codex는 ChatGPT 요금제에 들어 있습니다. 공식 요금 페이지 기준으로 Plus는 월 20달러, Pro는 월 100달러부터이고, Business는 연간 결제 시 사용자당 월 20달러(2인 이상), 월간 결제 시 25달러입니다. 요금표 기준으로 GitHub 코드 리뷰와 클라우드 연동은 Plus부터 들어 있고, Free와 Go는 데스크톱 앱 중심으로 안내돼 있습니다. 사용량은 5시간 단위 한도와 주간 한도로 관리되고, 로컬과 클라우드 작업이 같은 한도를 나눠 씁니다. ChatGPT의 Work 모드도 Codex와 한도를 함께 씁니다. 팀원이 Work로 보고서를 많이 만들면 Codex에 쓸 몫이 줄어드는 셈입니다.

API 키로 로그인하면 쓴 만큼 내는 방식이 됩니다. 대신 클라우드 작업, GitHub 리뷰, Slack 연동 같은 클라우드 기능은 쓸 수 없습니다. 회사 자료를 다룬다면 데이터 학습 여부도 따져야 합니다. Business 이상은 업무 데이터를 기본으로 학습에 쓰지 않고, Plus와 Pro는 개인이 직접 설정을 확인해야 합니다. 7단계의 원칙에 비춰 보십시오. Claude 쪽 요금과 한도는 Anthropic의 공식 안내에서 따로 확인합니다.

현실적인 출발점은 한쪽을 주력으로 두고 다른 쪽은 검토용으로 가볍게 쓰는 것입니다. 한 달 동안 어느 쪽 한도에 먼저 닿는지, 교차 검토가 실제로 무엇을 잡아냈는지 기록해 두면, 다음 달에 요금제를 조정할 근거가 됩니다. 94단계에서 다룰 에이전트 평가도 이 기록에서 시작합니다.

### 현장 장면
오세린 차장의 비품 신청 페이지는 이제 두 에이전트가 함께 손봅니다. 기능은 Claude Code가 만들고, PR마다 Codex가 자동 리뷰를 합니다. 첫 주는 순조로웠습니다. Claude Code가 붙인 월별 집계 화면에서 신청자 이름이 그대로 나가는 것을 Codex 리뷰가 잡아냈습니다. "신청자는 부서명만 보여 준다"는 규칙 위반이었습니다. 오 차장은 재현해 본 뒤 받아들였습니다.

둘째 주에 이상한 일이 생겼습니다. 신청일 표시 형식이 커밋마다 바뀌었습니다. Claude Code가 고친 PR에서는 "2026.10.15"였다가, Codex 클라우드에 맡긴 작은 수정 뒤에는 "2026-10-15"가 되고, 다음 Claude Code 작업에서 다시 점으로 돌아갔습니다. 오 차장은 두 규칙 파일을 나란히 열었습니다. CLAUDE.md에는 지난달 Claude Code와 작업하며 급히 넣은 "날짜는 YYYY.MM.DD로 쓴다"가 있었습니다. AGENTS.md에는 그 문장이 없고, `/init` 초안에서 온 "날짜는 ISO 형식(YYYY-MM-DD)"이 남아 있었습니다. 33단계에서 두 파일 맨 위에 "규칙을 고치면 두 파일을 함께 고친다"고 적어 두었지만, 그 문장도 결국 부탁이었습니다. 두 에이전트는 각자 받은 규칙을 충실히 지켰을 뿐입니다.

오 차장은 두 파일 맨 위에 "공통 규칙" 섹션을 같은 문장으로 두고, 날짜 형식을 하나로 정했습니다. 두 파일을 한 커밋에 함께 고치고, 커밋 메시지에 "공통 규칙 맞춤"이라고 적었습니다. 부탁만으로는 모자라니 확인하는 절차도 붙였습니다. 매달 첫 월요일에 아래 두 번째 프롬프트로 두 파일을 비교하는 일을 달력에 넣은 것입니다. 팀장에게는 이렇게 보고했습니다. "두 에이전트는 각자 받은 규칙대로 했습니다. 규칙을 다르게 준 건 저였습니다." 팀장은 웃으며 그 보고를 다음 달 요금제 논의 자료에 붙였습니다.

### 따라 하기
1. 위의 "어떤 일을 어디에 맡길까" 표를 복사해, 우리 팀의 실제 일 다섯 가지로 다시 씁니다. 성공 기준: 일마다 맡길 곳과 이유가 적혀 있습니다.
2. CLAUDE.md와 AGENTS.md를 아래 두 번째 프롬프트로 비교합니다. 성공 기준: 서로 어긋나는 규칙 목록을 받았습니다.
3. 두 파일 맨 위에 같은 문장의 "공통 규칙" 섹션을 두고, 어긋난 규칙을 하나로 정한 뒤 한 커밋에 함께 고칩니다. 성공 기준: 두 파일의 공통 규칙 섹션이 글자까지 같습니다.
4. Claude Code로 작은 기능 하나를 만들어 PR을 올리고 `@codex review`를 부릅니다. 성공 기준: Codex 리뷰가 달리고, 지적마다 판단이 적혀 있습니다.
5. 반대 방향으로 한 번 더 합니다. Codex에게 맡긴 변경을 Claude Code에게 아래 첫 번째 프롬프트로 검토하게 합니다. 성공 기준: 고친 파일 없이 보고만 돌아왔고, 두 검토 결과를 비교해 적었습니다.
6. 한 달 동안 두 도구의 사용량 한도에 닿은 날과, 교차 검토가 잡아낸 문제를 기록할 표를 만듭니다. 성공 기준: 첫 기록 하나가 들어 있습니다.

## 39단계 · 제2편 결과물 발표: 주소 하나로 시작한다

> 배포된 주소를 열어 보여 줍니다. 기준은 하나, 동료가 받아서 다음 주에 그대로 쓸 수 있습니까?

**걸리는 시간** · 읽기 약 10분 · 따라 하기 약 60분

### 이 단계를 마치면
- 발표에서 배포된 주소를 청중의 휴대폰으로 열게 하고, 중요한 동작을 실제로 보여 줄 수 있습니다.
- 동료의 결과물을 네 가지 기준으로 평가하고, 만든 쪽과 검토한 쪽이 누구였는지 물을 수 있습니다.
- 도구를 넘길 때 주소와 함께 저장소, CLAUDE.md와 AGENTS.md, 핵심 프롬프트, 교차 검토 기록을 묶어 넘길 수 있습니다.

발표 첫 화면에 슬라이드 대신 주소 하나가 떠 있습니다. 발표자가 말합니다. "지금 휴대폰을 꺼내 이 주소를 열어 보세요." 제2편의 발표는 이렇게 시작합니다.

이 단계로 제2편을 마무리합니다. 발표할 것은 20단계에서 동그라미를 친 바로 그 도구입니다. 제3부에서 Claude Code로 만들어 배포했고, 제4부에서 Codex로 기능을 넓히고 두 에이전트가 서로 검토하게 했습니다. 이제 그 도구에는 GitHub에 쌓인 기록과 남이 여는 주소, CLAUDE.md와 AGENTS.md라는 규칙 파일 두 개, 그리고 리뷰 지적마다 판단을 남긴 PR이 있습니다.

**발표의 중심은 주소다.** 과정을 설명하기 전에 결과부터 엽니다. 슬라이드에 화면 캡처를 붙이는 발표는 이 발표에 맞지 않습니다. 캡처는 내 노트북에서 된 것을 보여 줄 뿐, 남이 여는 주소에서도 된다는 것까지 보여 주지 못합니다. 발표를 시작하면 먼저 주소를 화면에 띄우고, 같은 주소를 청중에게 보내 각자 휴대폰으로 열게 합니다. 그 순간 청중 모두가 첫 사용자가 됩니다.

| 순서 | 하는 일 | 보여주는 것 |
|---|---|---|
| 열기 | 주소를 띄우고 청중에게 보내 각자 휴대폰으로 엽니다 | 남이 여는 주소가 있습니다 |
| 한 문장 | 누가, 언제, 무엇을 하려고 쓰는 도구인지 말합니다 | 범위가 정해져 있습니다 |
| 한 동작 | 가장 중요한 동작 하나를 실제로 눌러 보입니다. 청중도 같이 해 봅니다 | 실제로 동작합니다 |
| 한 사건 | 되돌린 일이나 검증·교차 검토에서 걸린 일 하나를 이야기합니다 | 어떻게 판단했는가 |

제2편에서 정말 보여 줘야 할 결과물은 판단의 과정입니다. 그래서 마지막 "한 사건"을 빼먹지 않습니다. 되돌린 커밋, 배포에서 막혀 로그를 읽은 일, 완료 보고를 믿지 않고 휴대폰에서 다시 확인한 일, Codex 리뷰의 지적을 화면에서 재현해 받아들이거나 반박한 일, 두 에이전트의 의견이 갈려 사람이 정한 일 같은 이야기입니다. 제4부 과제로 만든 교차 검토 비교표가 있다면 그대로 꺼내 보여 주면 됩니다. "누가 만들었고, 누가 봤고, 사람은 무엇을 판단했는가"에 답하는 데 이보다 좋은 자료는 없습니다.

**평가 기준.** 듣는 사람은 평가자가 됩니다. 과정 전체의 합격 기준을 그대로 씁니다. 다른 사람이 이 결과물을 받아 다음 주에 그대로 쓸 수 있습니까? 이 질문을 쪼개면 네 가지가 됩니다.

| 기준 | 확인하는 법 |
|---|---|
| 열리는가 | 청중이 자기 휴대폰으로 주소를 엽니다 |
| 동작하는가 | 중요한 동작을 청중이 직접 해 봅니다 |
| 이어받을 수 있는가 | CLAUDE.md·AGENTS.md와 커밋 기록, PR 댓글만 보고 무엇을 어떻게 고칠지 알 수 있습니다 |
| 안전한가 | 공개된 주소에 올라가면 안 될 정보가 없고, 저장소와 PR 댓글, 클라우드 환경 설정에 인증키가 없습니다 |

**발표 전 준비.** 발표 전날 30단계의 확인 절차를 한 번 더 밟습니다. 배포 목록의 마지막 배포가 준비됨인지, 본 주소가 최신인지, 제4부에서 합친 PR이 본 주소에 들어가 있는지, 휴대폰 데이터로도 열리는지 봅니다. 발표장 와이파이에서 주소가 열리는지도 미리 확인해 둡시다. 발표 도중 주소가 안 열리면 당황하지 말고 28단계의 순서를 그 자리에서 밟습니다. 브랜치, 캐시, 로그. 그 장면 자체가 좋은 발표 재료가 됩니다.

**넘기기.** 발표가 끝나면 도구를 실제로 팀에 넘깁니다. 이때 주소만 달랑 보내서는 안 됩니다. 저장소 주소, CLAUDE.md와 AGENTS.md, 이 도구를 만들 때 쓴 핵심 프롬프트, 그리고 교차 검토 기록을 함께 보냅니다. 그래야 받은 사람이 같은 방식으로 고쳐 가며 쓸 수 있습니다. 규칙 파일이 두 개 있으니 받은 사람이 Claude Code를 쓰든 Codex를 쓰든 같은 규칙에서 출발합니다. 저장소가 개인 계정에 있다면, 사내 도구로 계속 쓸 경우 회사 조직으로 옮기는 일정도 함께 정합니다.

왜 넘기기까지가 발표일까요. 만든 사람만 고칠 수 있는 도구는 만든 사람이 휴가를 가거나 부서를 옮기면 멈춥니다. 20단계 첫머리에서 본 엑셀 파일의 운명 그대로입니다. 주소만 받은 사람은 쓸 수는 있어도 고칠 수는 없습니다. 저장소와 규칙 파일, 핵심 프롬프트를 함께 받은 사람은 Claude Code나 Codex를 켜고 "규칙 파일을 읽고 이 문구를 바꿔 줘"라고 말하는 데서 바로 시작할 수 있습니다. 제2편에서 코드를 가르치지 않고 규칙을 정하고 기록하는 법을 익힌 까닭이 여기서 드러납니다.

### 흔한 오해와 실제
발표를 준비하는 수강생들이 자주 빠지는 생각이 있습니다.

"기능이 많아야 좋은 발표다." 청중은 기능 목록을 기억하지 못합니다. 자기 휴대폰에서 직접 눌러 본 한 동작을 기억합니다. 기능이 다섯 개라면 가장 중요한 하나만 보여 주고, 나머지는 "이런 것도 있다"며 짧게 넘어갑니다.

"평가에서 흠이 나오면 발표가 실패한 것이다." 이 시간은 애초에 흠을 찾으려고 모인 시간입니다. 발표자 혼자서는 자기 도구를 처음 쓰는 사람의 눈으로 볼 수 없습니다. 청중 여럿이 동시에 열어 보는 이 순간이 도구가 받을 수 있는 가장 값싼 검사입니다. 흠이 나오면 받아 적고, 어디를 고칠지까지 말하면 됩니다.

"발표가 끝나면 과제도 끝이다." 제2편의 합격 기준은 동료가 다음 주에 그대로 쓰는가입니다. 발표 당일에는 그 질문의 절반만 답할 수 있습니다. 나머지 절반은 넘기고 한 주가 지나야 보입니다.

### 청중과 도구에 따라 바꾸는 법
발표 순서는 같아도 청중에 따라 무게를 달리 둡니다. 청중이 같은 과정의 수강생이라면 "한 사건"에 시간을 가장 많이 씁니다. 다들 비슷한 막힘을 겪었기 때문에, 어떻게 판단했는지가 가장 쓸모 있는 이야기입니다. 청중이 임원이나 부서장이라면 "한 문장"과 "안전한가"에 무게를 둡니다. 누가 쓰는지, 무엇이 들어가지 않는지, 누가 만들고 누가 검토했는지, 틀리면 어떻게 되돌리는지를 먼저 말합니다. 청중이 실제로 쓸 팀원이라면 "한 동작"을 모두가 직접 해 보는 데 시간을 쓰고, 막히는 사람 옆으로 가서 어디서 멈췄는지 봅니다. 그 시간이 곧 사용자 시험입니다.

도구에 따라서도 달라집니다. 로그인이 필요하거나 회사망 안에서만 열리게 해 둔 도구라면 청중이 각자 여는 순서를 그대로 밟을 수 없습니다. 이럴 때 억지로 공개하지는 않습니다. 발표용 연습 계정이나 가공한 자료를 담은 미리보기를 따로 준비하되, 그것이 본 주소와 같은 코드에서 나온 것인지 배포 목록에서 확인해 둡니다. 청중이 열지 못한 부분은 오히려 "안전한가" 기준에서 점수가 됩니다. 왜 막아 두었는지 한 문장으로 설명하면 됩니다.

### 현장 장면
윤 과장의 발표는 주소 하나로 시작했습니다. 화면에 주소를 띄우고 같은 주소를 수강생 단톡방에 올렸습니다. "영업 사원이 외근을 마친 직후 휴대폰으로 방문 업종·지역, 만난 사람의 직함, 다음 약속을 적는 방문 일지입니다." 수강생들이 각자 휴대폰으로 주소를 열었습니다. 윤 과장은 기록 한 건을 적고, 브라우저를 닫았다 다시 열어 기록이 그대로 남아 있는 것을 보여 줬습니다. 청중도 똑같이 해 봤습니다. 이어서 도구가 거쳐 온 길을 한 문장으로 덧붙였습니다. "제3부에서 Claude Code로 만들었고, 제4부에서 Codex로 기능을 넓히면서 두 에이전트가 서로 검토했습니다." "한 사건"으로는 30단계의 일을 꺼냈습니다. 완료 보고를 믿고 단톡방에 올렸다가 다음 날 기록이 사라졌던 일, 되돌려도 통과하던 테스트 이야기였습니다.

평가 시간에 한 수강생이 손을 들었습니다. "내려받은 표를 열어 보니 작성자 이름이 전부 나오는데요?" 화면에는 성만 보이게 해 두었지만, 나중에 붙인 내려받기 기능에서 그 규칙이 빠진 것입니다. CLAUDE.md와 AGENTS.md의 공통 규칙에는 "화면에 사람 이름은 성만 보여 준다"라고 적혀 있었습니다. "화면에"라는 세 글자 때문에 내려받는 표는 규칙 밖에 놓여 있었습니다. 제4부에서 내려받는 표에 항목을 늘린 PR은 Codex 리뷰와 Claude Code의 검토를 모두 거쳤지만, 어느 쪽도 이 점을 지적하지 않았습니다. 둘 다 같은 규칙 문장을 기준으로 봤으니, 규칙에 빠진 곳은 두 에이전트 모두 보지 못한 것입니다. 교차 검토가 잡지 못한 흠을 청중이 잡은 셈이었습니다.

윤 과장은 그 자리에서 두 규칙 파일의 문장을 똑같이 "화면과 내려받는 파일 모두 사람 이름은 성만 쓴다"로 고치겠다고 적었습니다. 꼭 지켜져야 하는 규칙이니, 29단계에서 배운 훅으로 검사하게 하는 일도 다음 주 과제로 적었습니다. 발표가 끝난 뒤 윤 과장은 팀장에게 주소, 저장소 주소, CLAUDE.md와 AGENTS.md, 핵심 프롬프트 세 개, 교차 검토 비교표를 한 메시지로 보냈습니다. 팀장은 저장소를 회사 조직으로 옮기는 일을 IT팀에 요청하겠다고 답했습니다.

진짜 시험은 한 주 뒤였습니다. 윤 과장은 먼저 두 파일의 규칙 문장을 고치고, 내려받는 표의 작성자 항목에 성만 나오는지 Claude Code에게 확인 순서를 받아 직접 내려받아 열어 봤습니다. 성만 나왔습니다. 그다음 인수인계를 받은 같은 팀 김 대리에게 부탁했습니다. "제 도움 없이 입력 항목 이름 하나만 바꿔서 올려 봐 주세요." 김 대리는 영업본부에서 받은 ChatGPT 계정만 있었기 때문에 Codex를 켰습니다. AGENTS.md를 읽은 Codex에게 넘겨받은 핵심 프롬프트 하나를 고쳐 넣어 "다음 약속" 항목을 "다음 방문 예정일"로 바꾸게 했습니다. 커밋하고 푸시한 뒤에는 자기 휴대폰으로 같은 주소를 열어 바뀐 것을 확인했습니다. 무엇보다 반가운 것은 그동안 김 대리가 윤 과장에게 한 번도 묻지 않았다는 점이었습니다.

흠이 하나 남았습니다. 김 대리가 바꾼 항목 이름 때문에 예전 기록의 "다음 약속" 값이 표에서 비어 있었습니다. 30단계에서 겪은 저장 위치 이름 문제와 같은 종류였습니다. 김 대리는 그 커밋을 되돌리지 않고, 화면에 보이는 이름만 바꾸고 저장하는 이름은 그대로 두도록 다시 고치게 했습니다. 윤 과장은 이 일을 CLAUDE.md와 AGENTS.md의 "하지 말 것" 항목에 같은 문장으로 적었습니다. "저장하는 이름은 바꾸지 않는다. 바꿔야 하면 예전 기록을 옮기는 방법을 먼저 계획으로 받는다." 훅으로 이름 규칙을 검사하는 일과 저장소를 회사 조직으로 옮기는 일은 아직 남아 있습니다. 둘 다 날짜를 붙여 과제 목록에 올려 두었습니다.

### 따라 하기
1. 발표 전날 배포 목록의 마지막 배포가 준비됨인지 보고, 주소를 휴대폰 데이터로 열어 중요한 동작을 끝까지 해 봅니다. 성공 기준: 휴대폰에서 동작이 끝까지 되고, 본 주소가 최신입니다.
2. 도구를 "누가, 언제, 무엇을 하려고 쓰는 도구"인지 한 문장으로 적습니다. 성공 기준: 소리 내어 읽었을 때 한 호흡에 끝납니다.
3. 발표에서 주소를 띄우고 청중에게 보내 각자 열게 한 뒤, 중요한 동작을 함께 해 봅니다. 성공 기준: 청중 대부분이 도움 없이 열고 동작까지 해 봅니다.
4. 되돌리거나 걸렸던 일 하나를 이야기합니다. 교차 검토에서 두 에이전트의 의견이 갈렸던 일이나 Codex 리뷰의 지적을 재현해 본 일도 좋습니다. 성공 기준: 무엇이 잘못됐고 어떻게 알아챘고 어떻게 고쳤는지가 들어 있습니다.
5. 동료의 결과물을 네 가지 기준으로 평가하고, 지적받은 것을 다음 주 과제 목록에 적습니다. 성공 기준: 기준마다 예·아니오와 근거가 있습니다.
6. 아래 프롬프트로 인수인계 자료를 만들어 도구를 넘깁니다. Claude Code와 Codex 어느 쪽에 넣어도 됩니다. Codex에 넣을 때는 CLAUDE.md를 AGENTS.md로 바꿔 읽으면 됩니다. 성공 기준: 받은 사람이 주소, 저장소, CLAUDE.md와 AGENTS.md, 핵심 프롬프트, 교차 검토 기록을 한 번에 받았습니다.
7. (선택) 넘기고 한 주 뒤, 받은 사람에게 Claude Code든 Codex든 편한 도구로 도움 없이 문구 하나를 고쳐 푸시하게 하고 옆에서 지켜보기만 합니다. 막힌 곳이 있으면 그 내용을 두 규칙 파일이나 인수인계 자료에 보탭니다. 성공 기준: 받은 사람이 만든 사람에게 묻지 않고 고친 내용을 자기 휴대폰의 같은 주소에서 확인했습니다.

### 복사해 쓰는 프롬프트
```text
이 도구를 동료 [이름·역할]에게 넘기려고 해. 넘기기 전에 인수인계 자료를 만들어 줘.
- 이 도구가 무엇이고 누가 언제 쓰는지 세 줄
- 배포된 주소와 저장소 주소를 적을 곳
- 가장 중요한 동작과 그것을 휴대폰에서 확인하는 순서
- 자주 고칠 만한 것과 고치는 방법을 Claude Code에게 요청하는 문장 예시
- CLAUDE.md에 빠진 규칙이 있다면 추가 제안(고치지는 말고 제안만)
- 공개 주소와 내려받는 파일에 있으면 안 될 정보가 들어 있는지 점검한 결과
확인하지 못한 항목은 확인하지 못했다고 적어 줘.
```

### 막히면 이렇게
| 증상 | 원인 | 처방 |
|---|---|---|
| 발표장에서 주소가 안 열립니다 | 발표장 망이 막거나, 마지막 배포가 실패했습니다 | 휴대폰 데이터로 열어 보고, 배포 목록의 상태를 확인합니다 |
| 청중 화면이 내 화면과 다릅니다 | 캐시이거나 다른 브랜치의 미리보기 주소를 보냈습니다 | 본 주소를 다시 보내고 시크릿 창으로 열게 합니다 |
| 평가에서 규칙 위반이 나왔습니다 | 새 기능에서 규칙이 빠졌습니다 | 규칙 문장을 넓혀 CLAUDE.md와 AGENTS.md에서 같은 문장으로 고치고, 꼭 지켜야 하면 훅 후보로 적습니다 |
| 교차 검토를 통과했는데 평가에서 흠이 나왔습니다 | 두 에이전트가 같은 규칙 문장을 기준으로 봤습니다 | 규칙 문장에 빠진 경우가 없는지 사람이 다시 읽고, 발표 평가를 세 번째 검토로 삼습니다 |
| 넘겨받은 사람이 고친 뒤 예전 기록이 안 보입니다 | 저장하는 이름까지 바뀌었습니다 | 화면 이름만 바꾸게 다시 고치고, 두 규칙 파일의 "하지 말 것" 항목에 적습니다 |

### 스스로 점검
- [ ] 캡처 대신 배포된 주소로 발표를 시작했고, 청중이 자기 휴대폰으로 열어 중요한 동작을 해 봤습니까?
- [ ] "한 사건"에서 누가 만들고 누가 검토했으며 사람이 무엇을 판단했는지 이야기했습니까?
- [ ] 도구를 넘길 때 주소, 저장소, CLAUDE.md와 AGENTS.md, 핵심 프롬프트, 교차 검토 기록을 함께 넘겼습니까?

### 기억할 것
- 발표 기준은 하나입니다. 동료가 다음 주에 그대로 쓸 수 있습니까?
- 발표는 주소를 여는 데서 시작하고, 넘길 때는 주소와 함께 저장소, 두 규칙 파일, 핵심 프롬프트, 교차 검토 기록을 넘깁니다.
- 교차 검토는 규칙 문장이 빠뜨린 곳까지 잡아 주지 않습니다. 청중의 눈이 그다음 검토입니다.

## 제4부를 마치며

아홉 단계를 지나는 동안 오세린 차장은 에이전트 하나에 기대던 사람에서, 두 에이전트에게 일을 나눠 주고 서로 검토하게 하는 사람이 됐습니다. 새로 배운 명령은 많았지만 원리는 제3부와 같았습니다. 규칙은 파일에 적고, 큰일은 계획부터 받고, 작업 전후로 커밋하고, 끝났다는 보고는 배포된 주소에서 직접 확인합니다. 달라진 것은 확인의 겹이 하나 늘었다는 점입니다. 만든 쪽이 아닌 다른 에이전트가 PR을 읽고, 사람은 그 지적을 화면에서 재현해 받아들일지 정합니다.

두 도구를 함께 쓰면 편해지는 만큼 관리할 것도 늘어납니다. 규칙 파일이 둘이 되고, 구독이 둘이 되고, 사용량 한도도 따로 봐야 합니다. 그래서 이 부의 마지막 습관은 기록입니다. 어느 일을 어디에 맡겼는지, 교차 검토가 무엇을 잡아냈는지, 어느 쪽 한도에 먼저 닿았는지를 한 달만 적어 보면, 다음 달에 무엇을 바꿀지가 보입니다. 아래 항목을 하나씩 확인해 보십시오.

- [ ] `codex --version`이 버전 번호를 돌려주고, `codex login status`로 ChatGPT 계정 로그인을 확인했습니다.
- [ ] 내 도구의 저장소 맨 위에 AGENTS.md가 있고, CLAUDE.md와 같은 문장의 공통 규칙이 들어 있습니다.
- [ ] 승인 방식과 샌드박스를 내 작업에 맞게 골랐고, 전부 허용 설정은 쓰지 않았습니다.
- [ ] 코딩 없는 파일 정리 한 건을 Codex로 처리하고, 건수와 원본 보존을 직접 확인했습니다.
- [ ] 클라우드 환경을 만들어 인터넷을 Off로 둔 채 두 작업을 나란히 돌리고, 결과를 PR로 받아 합쳤습니다.
- [ ] 내 저장소에 Codex 코드 리뷰를 켜고, 지적마다 받아들임·보류·반박 가운데 하나를 골라 이유를 남겼습니다.
- [ ] config.toml의 주요 설정을 읽을 수 있고, `codex exec`로 읽기 전용 점검 하나를 돌려 봤습니다.
- [ ] 한쪽이 만든 변경을 다른 쪽이 고치지 않고 검토만 하게 하는 교차 검토를 끝까지 해 봤습니다.
- [ ] 제2편 결과물을 배포된 주소로 발표하고, 주소·저장소·두 규칙 파일·핵심 프롬프트·교차 검토 기록을 함께 넘겼습니다.

### 이 부의 과제
**과제 이름.** 제3부에서 만든 사내 도구를 Codex로 한 단계 넓히고, 두 에이전트의 교차 검토를 거쳐 배포합니다.

**할 일.**
1. 제3부 도구의 저장소에 AGENTS.md를 만들고, CLAUDE.md와 같은 문장의 공통 규칙 섹션과 `## Code Review Rules` 섹션을 넣습니다.
2. 새 기능이나 개선 두 가지를 정해, 서로 겹치는 파일이 없게 나눈 뒤 Codex(Local, Worktree, Cloud 가운데 하나 이상)에게 맡깁니다.
3. 결과를 PR로 올리고 `@codex review`로 리뷰를 받습니다. 지적마다 판단과 이유를 PR 댓글로 남깁니다.
4. 같은 PR을 Claude Code에게 고치지 말고 검토만 하게 해서, 두 검토 결과를 비교합니다.
5. 받아들인 지적만 고치고 합친 뒤, 배포된 주소를 휴대폰으로 열어 가장 중요한 동작을 확인합니다.
6. `codex exec`로 읽기 전용 점검 하나를 만들어 한 번 돌리고, 결과 파일을 남깁니다.

**제출물.**
1. 배포된 주소 하나. 본줄 기준의 본 주소여야 합니다.
2. GitHub 저장소 주소. 비공개로 두고, 평가자에게 읽기 권한을 줍니다.
3. 저장소 맨 위의 AGENTS.md와 CLAUDE.md. 공통 규칙 섹션이 같은 문장이어야 합니다.
4. Codex 리뷰를 받은 PR 주소 하나. 지적마다 판단과 이유가 댓글로 남아 있어야 합니다.
5. 교차 검토 비교표. Codex 리뷰와 Claude Code 검토가 각각 무엇을 지적했는지, 겹친 것과 한쪽만 잡은 것, 사람이 어떻게 판단했는지를 적습니다.
6. `codex exec` 점검 명령과 그 결과 파일.
7. 한 쪽짜리 메모. 어떤 일을 어느 에이전트에 맡기기로 했는지와 그 이유, 한 달 동안 기록할 항목(한도에 닿은 날, 교차 검토가 잡아낸 문제)을 적습니다.

**완료 기준.**
- 평가자가 자기 휴대폰으로 주소를 열고, 새로 넣은 기능을 도움 없이 끝까지 써 봅니다.
- PR의 리뷰 지적 가운데 판단이 적히지 않은 것이 하나도 없습니다.
- 교차 검토 비교표에 한쪽 에이전트만 잡아낸 항목이 하나 이상 있거나, 없었다면 없었다고 적혀 있습니다.
- 평가자가 AGENTS.md와 CLAUDE.md의 공통 규칙을 나란히 놓았을 때 글자까지 같습니다.
- `codex exec` 점검을 돌린 뒤 `git status`에 바뀐 파일이 없습니다.
- 저장소, 커밋 기록, PR 댓글, 클라우드 환경 설정 어디에도 인증키·비밀번호·실제 고객 정보가 없습니다.

여기까지 왔다면 에이전트 하나에게 맡기고 확인하는 법에서 한 걸음 나아가, 두 에이전트에게 일을 나누고 서로 검토하게 하는 법을 손에 익힌 셈입니다. 39단계의 발표로 제2편도 마무리했습니다. 다음 제3편의 제5부에서는 일하는 곳을 폴더 밖으로 넓힙니다. 로그인해야 들어가는 사이트를 돌며 조사하고 입력하는 일을 브라우저 안의 AI에게 맡기고, 44단계에서는 브라우저 밖의 앱까지 맡깁니다. 대상이 파일에서 화면으로 바뀌어도 여기서 익힌 원칙, 즉 읽기 전용에서 시작하고 만든 쪽과 보는 쪽을 나누고 판단은 사람이 한다는 원칙은 그대로 따라갑니다. 뒤에서 자동화(74~76단계)와 에이전트 평가(94단계)를 다룰 때도 다시 쓰입니다.
